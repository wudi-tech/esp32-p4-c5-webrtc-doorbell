## 第 1 章 先建立 5 个正确的心智模型

在打开任何一个 `.c` 文件之前，先记住这 5 句话。它们是理解全部代码的钥匙。

**模型 1：这是一个"单设备自给自足"的系统。**
本项目没有云端、没有第二台服务器。ESP32-P4 自己就是网页服务器、自己就是信令服务器、自己就是媒体端点。浏览器访问的是板子的 IP。所以"信令"这种通常由服务器承担的角色，在本项目里是板子上一段 HTTPS 服务器代码（`webrtc_http_server.c`）。

**模型 2：整个项目 = 上游框架 + 一个应用目录。**
仓库里绝大部分代码不是你写的：`components/` 是 Espressif 的通用库，`solutions/` 下还有 11 个别的示例。你的作品集中在 `solutions/doorbell_local/`（约 1.1 万行自有代码），以 `solutions/doorbell_local/main/` 为业务核心。汇报时先说清这条边界，后面所有"这是什么"的问题都会变得简单。

**模型 3：三条互不相同的通信通道，千万不要混。**
- **下行（板 → 网页）**：SSE（服务器发送事件），一条 `GET /webrtc/signal` 长连接，板子主动往里推 JSON。
- **上行（网页 → 板）**：HTTP POST，`POST /webrtc/signal/post`，网页每次发一条 JSON。
- **媒体（音视频本身）**：WebRTC（SRTP over DTLS over UDP），完全不经过 HTTP。

很多人以为网页和板子用了 WebSocket，其实没有。SSE + POST 是"轻量信令"，WebRTC 才是"重媒体"。

**模型 4：应用层是"状态机 + 多线程 + 回调"的组合，不是一路顺序执行。**
板子上同时跑着：WebRTC 内部任务、BOOT 按键轮询任务、HTTP 服务器任务、SSE 推送任务、AI 推理任务、雷达 UART 任务、舵机任务、提示音任务。它们通过**互斥锁（mutex）+ 状态变量 + 队列**协作。看懂 `door_bell_state` 和四把锁，就看懂了 `webrtc.c`。

**模型 5：感知是"双证据"设计，不是单传感器。**
雷达负责"门前 3 米内有没有东西进来"，摄像头负责"那个东西是不是人"。两者都满足才自动按门铃。这是本作品和上游例程最大的设计差异，也是最容易被追问的点。

## 第 2 章 从零看懂一个嵌入式工程的组织方式

### 2.1 ESP-IDF 工程的三层结构

```
工程目录（solutions/doorbell_local/）
├── CMakeLists.txt          ← 工程入口，指定 IDF 构建系统
├── partitions.csv          ← Flash 分区表（nvs / app / 模型）
├── sdkconfig.defaults*     ← 芯片、外设、内存的默认配置
└── main/                   ← 默认组件（component），里面才是代码
    ├── CMakeLists.txt      ← 登记源文件 + 嵌入资源
    ├── idf_component.yml   ← 声明外部依赖（AI 模型、组件库）
    ├── Kconfig             ← 定义一个功能开关
    └── *.c / *.h / *.html  ← 业务源码
```

要点：
- `main/` 是一个 ESP-IDF "component"。`idf_component_register()` 决定哪些 `.c` 会被编译、哪些资源会被"嵌入固件"。
- `EMBED_TXTFILES` 把 `ring.aac`、`open.aac`、`join.aac`、`webrtc_test.html`、证书打进固件，编译后生成符号 `_binary_ring_aac_start` 等，代码里用 `extern` 直接访问（见 `media_sys.c:72`、`webrtc.c:101`、`webrtc_http_server.c:353`）。**这说明网页和提示音不在文件系统里，而在固件的只读数据段中。**
- `partitions.csv` 里的 `pedestrian_det` 分区（500K）是给 AI 模型用的。

### 2.2 你改了什么、继承了什么的判据

判断一个文件是否属于"本项目自有"：

- 在 `components/` 下 → 上游通用库；
- 在 `solutions/` 其他子目录 → 上游其他示例，与本次提交无关。

## 第 5 章 开机到可用的完整启动流程

### 5.1 逐行走一遍 `app_main()`

打开 `main.c:435`。这 45 行决定了整个系统的装配顺序，**顺序本身就是设计**：

```c
void app_main(void)
{
    esp_log_level_set("*", ESP_LOG_INFO);          // 1. 日志
    media_lib_add_default_adapter();               // 2. 让 media_lib_* 绑定到 FreeRTOS/lwIP
    esp_capture_set_thread_scheduler(capture_scheduler);  // 3. 采集管线线程策略
    media_lib_thread_set_schedule_cb(thread_scheduler);   // 4. 全局线程策略
    init_board();                                  // 5. 音频 codec + 板级
    if (doorbell_webrtc_init() != 0) return;       // 6. 先建锁，再允许任何回调
#ifdef CONFIG_DOORBELL_SUPPORT_PEDESTRIAN_DETECT
    multimodal_fusion_init(...);                   // 7. 融合器
    media_lib_mutex_create(&sensor_fusion_mutex);  //    融合器自己的锁
#endif
    door_lock_init();                              // 8. 舵机 PWM
    presence_fusion_init(...);                     // 9. 雷达状态机
    radar_ld2450_init(radar_frame_received, NULL); //10. 雷达 UART（此后回调可能随时发生）
    media_sys_buildup();                           //11. 摄像头 + 播放器 + 提示音预处理
    init_console();                                //12. 串口命令行
    network_init(WIFI_SSID, WIFI_PASSWORD, network_event_handler); //13. Wi-Fi
    while (1) { media_lib_thread_sleep(2000); query_webrtc(); }    //14. 主循环探活
}
```

**为什么第 6 步必须在第 8/10 步之前？**
`doorbell_webrtc_init()` 只做一件事：创建 4 把互斥锁（`webrtc.c:136-185`）。雷达回调、BOOT 任务、HTTP 回调都可能调用同一个来电入口 `doorbell_request_ring()`，而它一进来就检查锁是否存在。**先有锁，后有回调**，否则会出现"回调已触发但同步对象还是 NULL"的竞态。

**为什么雷达初始化和媒体构建之间没有依赖？**
雷达走 UART，媒体走摄像头/I2S，互不依赖。但雷达一旦初始化，回调就可能立刻触发并去发布 SSE，所以它放在 `media_sys_buildup()` 之前或之后都可以——代码选择了"先把能触发事件的放前面"。

**第 13 步的回调是关键跳点**：

```c
static int network_event_handler(bool connected)   // main.c:420
{
    if (connected) {
        RUN_ASYNC(start, {                         // 用新线程做，避免阻塞 Wi-Fi 事件任务
            start_webrtc(NULL);
            ESP_LOGI(TAG, "Use browser to enter https://%s/webrtc/test for test", ...);
        });
    } else {
        stop_webrtc();
    }
}
```

`RUN_ASYNC` 是个宏（`main.c:216-222`），展开成"创建一个线程，执行花括号里的代码，然后销毁自己"。**为什么不能直接在事件回调里 `start_webrtc()`**？因为 `start_webrtc()` 内部要建 HTTPS 服务器、开 WebRTC、等锁，耗时较长；Wi-Fi 事件任务被阻塞会影响协议栈。

### 5.3 线程与栈：为什么调度器要单独写一个函数

`thread_scheduler()`（`main.c:361-395`）在**每个** `media_lib` 线程被创建时被回调，按线程名定制栈和优先级。这解决了三个真实问题：

| 线程名 | 定制 | 原因（对话术） |
| --- | --- | --- |
| `venc_0` | 优先级 10，S3 上 20 KB 栈 | H.264 软编码需要大栈和稳定时间片 |
| `aenc_0` | 40 KB 栈、核心 1 | OPUS 编码栈需求大（本项目用 G711A 时可小） |
| `AUD_SRC` | 优先级 15 | 音频采集必须及时，否则断音 |
| `detect` | 24 KB 栈、优先级 8 | **曾经的故障点**：4 KB 栈 + 浮点格式化触发栈保护重启；提高栈并降优先级后连续观察 7 分钟无异常 |
| `detect_filter` | 优先级 15 | 拿帧、降采样、投递队列要及时，否则丢帧 |
| `pc_task` | 25 KB 栈、核心 1 | PeerConnection 主循环重，绑到核心 1 避开核心 0 上的媒体管线 |

`capture_scheduler()`（`main.c:397-409`）把 `esp_capture` 的线程参数转成 `media_lib` 的参数，并强制 `stack_in_ext = true`（栈分配在 PSRAM）。**P4 的片内 RAM 有限，线程栈放外部 PSRAM 才能开这么多任务。**

## 第 6 章 五条核心业务流程（从 API 到 API）

看懂这 5 条链路，就掌握了 80% 的代码。每条都给出"触发 → 调用 → 结果"。

### 6.1 流程一：来电（BOOT 按键 / 雷达 / 传感器融合）

三种触发源最终都汇到**同一个入口** `doorbell_request_ring(source)`（`webrtc.c:333`）。这是本项目的核心设计模式：**多来源 → 单入口 → 单状态机**。

```text
触发源 A：BOOT 按键
  key_monitor_thread (webrtc.c:1091)  每 50 ms 读 GPIO35
    └─ 电平相对"启动电平"发生变化 → doorbell_request_ring("boot")

触发源 B：雷达
  radar_uart_task (radar_ld2450.c)
    └─ ld2450_stream_feed → ld2450_parse_frame
       └─ radar_frame_received (main.c:141)
          └─ presence_fusion_process → event == ENTER_CONFIRMED
             └─ doorbell_request_ring("radar")

触发源 C：雷达 + 视觉融合（启用 AI 时取代 B）
  radar_frame_received → multimodal_fusion_on_radar(true, ring_eligible, now)
  doorbell_report_vision_snapshot (main.c:86)
    → multimodal_fusion_on_vision_evidence(evidence, ts)
       两者都满足且本次来访未响过 → request_sensor_ring("radar+vision")

                         ↓ 三源合一
  doorbell_request_ring(source)  (webrtc.c:333-405)
    1) 加锁 webrtc_api_mutex + door_bell_mutex
    2) doorbell_ring_policy_evaluate(webrtc != NULL, state == NONE)
         → NOT_READY / BUSY / ACCEPTED
    3) ACCEPTED：把 door_bell_state 置为 RINGING，并 ++ring_generation（"预占"）
    4) SEND_CMD(RING)  经信令通道发给浏览器
    5) play_tone(TONE_RING)  板端自己响铃（ring.aac）
    6) schedule_ring_stop(...)  起一个线程，4 秒后若仍是 RINGING 且代号未变，
       发 RING_STOPPED 让网页停铃；代号（generation）防止"旧请求关掉新铃声"
```

**三个必须能讲清的工程细节：**

1. **为什么要有 `ring_generation`？** 因为"4 秒后停铃"是一个延时线程，如果这 4 秒内用户挂断又重新来电，旧线程不能把新铃声关掉。代号不匹配就不发。
2. **`DOORBELL_RING_BUSY` 的意义**：正在响铃或通话中再次触发，直接拒绝并打日志。这就是"防重复呼叫"的实现，而不是靠延时去抖。
3. **板端响铃和网页响铃是两套**：板端 `play_music(ring.aac)`，网页 `<audio>` 播放 `GET /webrtc/ring.aac`（同一个文件由 HTTPS 提供，`webrtc_http_server.c:363`）。`RING_STOPPED` 是两者同步的握手，网页另有 4.5 秒超时兜底。

### 6.2 流程二：接听并建立媒体

```text
网页点击"接听" (webrtc_test.html:812)

  → POST /webrtc/signal/post  {"type":"customized","data":"ACCEPT_CALL"}
  → webrtc_signal_post_handler (webrtc_http_server.c:214)
      → cJSON 解析 → msg.type = CUSTOMIZED
      → sig_cfg.on_msg(&msg, ctx)   ← 这是 esp_webrtc 注册进来的回调
      → esp_webrtc.c: signal_new_msg() (esp_webrtc.c:708)
          → rtc_cfg.peer_cfg.on_custom_data(...)
              → door_bell_on_cmd() (webrtc.c:557)

  door_bell_on_cmd 收到 "ACCEPT_CALL"：
      door_bell_change_state_locked(CONNECTING)
      schedule_peer_connection_change(handle, enable=true, expected=CONNECTING, previous=旧状态)
          → 起线程 peer_enable → esp_webrtc_enable_peer_connection(handle, true)

  esp_webrtc_enable_peer_connection (esp_webrtc.c:773)：
      pending_connect = false
      → start_peer_connection() 用 ice_info（含 ICE 角色/STUN）建 PeerConnection
      → esp_peer_new_connection() 产生 offer/answer 流程
```

**SDP/ICE 的往返路径**（理解"两个方向不对称"是重点）：

| 方向 | 载体 | 代码位置 |
| --- | --- | --- |
| 板 → 浏览器（offer/answer/candidate/customized） | SSE `data: {...}` | `webrtc_http_server_send_msg()` `:514` |
| 浏览器 → 板（offer/answer/candidate/customized） | HTTP POST JSON | `webrtc_signal_post_handler()` `:214` |
| 板收到 answer 时的额外处理 | 从 SDP 文本里逐行提取 `a=candidate:` 单独投递 | `:294-311` |
| 板发出 SDP 时的额外处理 | 把 SDP 里的候选重新逐条发一遍 | `resend_all_candidate()` `:491` |

**为什么要拆候选？** 因为简化的 HTTP 信令没有独立的 trickle-ICE 通道时，把候选嵌在 SDP 里是最省事的；两边都做了"拆/合"的兼容处理，保证候选不会丢。

**浏览器端**（`webrtc_test.html:1139-1230`）：
- `iceServers: []`——**局域网直连，不配置 STUN/TURN**（这是把接通时间从 ~30 秒降到 4～6 秒的关键改动之一）；
- `createDataChannel('channel1')` 与 `'channel2')` 两条数据通道，用于大消息收发自测；
- `ontrack` 把远端音视频挂到 `<video>`；
- `oniceconnectionstatechange` 在 `failed` 时 `restartIce()`。

**连接成功信号**：板端 `ESP_WEBRTC_EVENT_CONNECTED` → `door_bell_change_state(CONNECTED)`（`webrtc.c:1055`）。板端状态机此时才允许"通话中开门走混音路径"。

### 6.3 流程三：挂断（为什么是"确认式挂断"）

```text
网页点"挂断" (webrtc_test.html:833 requestHangup)
  → 立刻显示"正在挂断"，但**不立即关连接**
  → POST DENY_CALL
  → door_bell_on_cmd: 状态置 DISCONNECTING
      → schedule_peer_connection_change(enable=false, expected=DISCONNECTING)
          → 线程里 esp_webrtc_enable_peer_connection(false)
              → 内部 pc_close() 释放 PeerConnection、停止流
          → 成功则再发 CALL_ENDED，失败则发 CALL_END_FAILED
  → 网页收到 CALL_ENDED → finalizeHangup() (webrtc_test.html:861)
      → 关闭 PeerConnection、停止本地麦克风、清空 video.srcObject、重置 UI
  → 若 3 秒内没等到确认：显示"开发板无法结束通话，请重试"，不清状态
```

**为什么要这样绕一圈？** 早期版本网页一按挂断就自己清状态，结果出现"网页显示通话结束但视频仍在播"——因为板端连接没真的关。改成"以板端确认作为唯一结束条件"后问题消失。这是**状态一致性优先于响应速度**的典型取舍，汇报时值得强调。

**断线宽限**：`DISCONNECT_GRACE_PERIOD_MS = 15000`（`webrtc_test.html:519`）。Wi-Fi 抖动导致 ICE 短暂 `disconnected` 时，15 秒内不主动挂断；恢复即继续通话。

### 6.4 流程四：通话中开门 + 语音提示（本项目最有技术含量的一段）

```text
网页点"开门" (webrtc_test.html:830)
  → POST {"type":"customized","data":"OPEN_DOOR"}
  → door_bell_on_cmd 分支 (webrtc.c:574)
      ├─ door_lock_request_open()：只把请求投进队列，立刻返回
      │     door_lock_task (door_lock.c)：
      │       状态 LOCKED → OPENING → 2500 us 脉宽 → 等 500 ms
      │       → UNLOCKED → 保持 5000 ms → CLOSING → 500 us → 等 500 ms → LOCKED
      │       每次状态变化通过 door_lock_set_state_callback 回调
      │         → door_lock_state_changed (webrtc.c:407)
      │             → SEND_CMD(DOOR_OPENING / DOOR_OPENED / DOOR_CLOSING / DOOR_LOCKED / DOOR_FAILED)
      │             → 网页据此显示中文提示并禁用按钮
      └─ 语音提示分三条路：
           通话中 (CONNECTED) → play_open_door_prompt_in_call()
           连接中/响铃中   → 不播提示音（避免抢音频通道）
           空闲           → play_tone(TONE_OPEN_DOOR)（走普通播放器）
```

**核心技术点：`pcm_overlay` + 自定义 audio render。**

问题的本质：`av_render` 的音频输出（I2S → ES8311）是**独占**的。通话时远端音频正在往里写；此时再让 `play_music()` 打开一路 AAC 流去播放，就会互相打断——这就是早期"开门语音只能在挂断后听到"的原因。

解法（`doorbell_audio_render.c`）：
1. 启动时先用 `av_render_alloc_prompt_overlay()` 包一层自定义 render（`:223`），它内部仍然持有真正的 I2S render，但拦截了 `write`；
2. 开门语音在 `media_sys_buildup()` 阶段就被**离线解码**成 16 kHz 单声道 PCM 常驻内存（`media_sys.c:152 prepare_open_door_prompt()`，自己解析 ADTS 头逐帧解码 + 重采样）；
3. 通话中调用 `doorbell_audio_prompt_start()` 把这段 PCM "装载"进叠加器（`:252`）；
4. 远端音频每写一帧，`prompt_render_write()`（`:147`）先调 `pcm_overlay_mix_mono()` 把提示音**逐样本加到远端 PCM 上**并做 16 位饱和限幅，再交给真正的 I2S render；
5. 如果远端长时间没有音频（例如对方静音），`prompt_fallback_worker`（`:38`）在检测到 40 ms 静音后自己输出静音帧承载提示音，保证提示音不会因为"远端没声音"而卡住。

**汇报话术**：*"我们没有新增一路音频通道，而是在 WebRTC 的音频渲染回调里做了一次样本级混音，用饱和限幅保证不削顶，所以通话不会中断、提示音也不会延迟到挂断之后。"*

> **⚠️ 讲这句之前必须先做一件事**（这是全篇最重要的一条自查）
>
> 混音路径有一个前置条件：当前音频必须是 **16000 Hz、1 或 2 声道、16 bit**（`doorbell_audio_render.c:134-137` 的 `compatible` 判断）。而本项目默认构建**没有定义 `WEBRTC_SUPPORT_OPUS`**，通话音频走的是 **G711A / 8000 Hz / 单声道**（`webrtc.c:1226-1228`）。
>
> 实测日志印证了这一点：一次真实通话里渲染器打开的是 8000 Hz（`docs/bringup/logs/webrtc-aac-assets-runtime-20260902.log:454,463` 的 `Get samplerate 8000` / `I2S_RENDER: open channel:1 sample_rate:8000`），而上一段 16 kHz 只出现在启动阶段的 `join.aac`（同文件 `:212,214`，采样率 16000）。
>
> 由此推出两个后果：
> 1. `pcm_overlay_mix_mono()` 分支**不会执行**（`compatible == false`）；
> 2. 兜底线程在 `!compatible` 时直接 `continue`，**也不会输出**（`doorbell_audio_render.c:56-60`）。
>
> 也就是说：**在默认 G711A 构建下，通话中点开门不会有任何语音提示**；而且 `play_open_door_prompt_in_call()` 仍返回 0，串口不会有任何警告——这属于"静默失效"，最难在演示现场发现。
>
> 开发日志里"新增 PCM Overlay 后通话中能听到开门播报"的记录（`01_开发日志.md:112`），与当时的实机验收状态并不一致：2026-09-08 的验证记录把"通话中听到口头提示"明确列为**待用户实机确认**（`docs/bringup/logs/2026-09-08-chinese-ui-prompt-fallback.md:42-53`，期望日志序列 `Prompt playback armed` → `Prompt mixed...` 或 `Prompt fallback output...` → `Prompt playback completed`，尚待勾选）。
>
> **提交前必须做的三件事**：
> 1. 按最终固件在实机上实测"通话中点开门"，看串口是否出现上面三段日志中的**后两段**；
> 2. 选一个修法：① 启用 `WEBRTC_SUPPORT_OPUS`（通话走 16000 Hz，混音分支直接生效）；② 扩展 `compatible` 判定到 8 kHz 并加对应重采样；③ 把 `open.aac` 预处理目标改成 8 kHz，让 8 kHz 路径也能混音（改 `media_sys.c:163-167`）；
> 3. 修完后再决定文档与汇报口径。
>
> **在没复测、没修复之前，汇报里不要说"通话中能听到开门语音"**。可以说："开门播报做了预解码 PCM 输出通道，目标是与通话音频共用同一条 I2S 输出；当前默认 8 kHz 音频配置下该路径需要复测/修正。"

### 6.5 流程五：感知链路（雷达 + 视觉）与规则"双证据"

**雷达侧**（`radar_ld2450.c` + `presence_fusion.c`）：

```text

**视觉侧**（`pedestrain_detect.cpp` + `vision_tracker.c`）：

```

**融合判定**（`multimodal_fusion.c`，全文只有 82 行，是"少代码高价值"的典型）：

```c
request_ring_if_fused():
    雷达在区(radar_present) && 本次进入允许响铃(radar_ring_eligible)
    && 本次来访尚未响过(!ring_emitted_for_visit)

  → 返回 true，并把 ring_emitted_for_visit 置位
```

- **2 秒证据窗口**：`vision_valid_ms = 2000`。雷达先进区、人再走进画面，或者反过来，都能在 2 秒内配对成功。
- **一次来访只响一次**：`ring_emitted_for_visit` 在雷达"离开"时清零。
- **为什么不用单传感器**：纯雷达会被门外经过的物体误触发；纯视觉受光线和分辨率影响。双证据把误触发概率显著压低。**注意措辞：这是"降低误触发"，不能宣称"消除误报"。**

**汇报时必须守住的事实边界**（评委最爱追问）：
- 摄像头只判断"有没有人 / 有没有人脸存在"，**不做身份识别**；
- 页面上显示的百分比是**该框的模型置信分数**，不是系统准确率；
- LD2450 输出最多 3 个**二维目标点**，不是点云、不是俯视图；
- 网页"检测事件数"是**累计历史条数**，不是当前人数。

## 第 7 章 WebRTC 会话层：esp_webrtc 是什么、你用它做了什么

### 7.1 `esp_webrtc` 帮你省掉了什么

如果不看 `components/esp_webrtc`，很容易误以为"WebRTC = 一堆 UDP 打洞代码"。实际分工是：

| 层次 | 谁负责 | 具体内容 |
| --- | --- | --- |
| 会话编排 | `esp_webrtc` | 把"信令实现 + PeerConnection 实现 + 采集/播放 + 编解码"组装成一件事，提供 `esp_webrtc_open/start/enable_peer_connection/close/query` |
| 协议实现 | `esp_peer` | ICE/STUN、DTLS、SRTP、SCTP 数据通道、RTP 变换钩子 |
| 信令实现 | `webrtc_http_server.c`（本项目） | `esp_peer_signaling_impl_t` 的 `start/send_msg/stop` 三个函数 |
| 媒体实现 | `esp_capture` + `av_render` | 采集编码/解码播放 |

`start_webrtc()` 里那段配置结构（`webrtc.c:1218-1255`）就是"把上面四块拼起来"的清单：

```c
esp_webrtc_cfg_t cfg = {
    .peer_cfg = {
        .audio_info = { G711A, 8000, 1 },          // 或 OPUS 16000/2（WEBRTC_SUPPORT_OPUS）
        .video_info = { H264, 640, 480, 15 },      // 来自 settings.h
        .audio_dir  = SEND_RECV,                   // 双向音频
        .video_dir  = SEND_ONLY,                   // 板 → 浏览器单向视频
        .on_custom_data = door_bell_on_cmd,        // 浏览器命令入口
        .on_channel_open/on_data/on_channel_close = ...,  // 数据通道
        .enable_data_channel = true,
        .manual_ch_create    = true,               // 不自动建通道（浏览器是 SCTP 客户端）
        .no_auto_reconnect   = true,               // 信令一连上不自动开会话
        .extra_cfg = &peer_cfg,                    // agent_recv_timeout = 500
    },
    .signaling_cfg = { .signal_url = url },        // NULL → 用本地 HTTP 信令
    .peer_impl      = esp_peer_get_default_impl(),
    .signaling_impl = esp_signaling_get_http_impl(),  // ← 你写的那个
};
```

### 7.2 `no_auto_reconnect` + `enable_peer_connection`：门铃"必须有人接听"的实现

这是本项目相对上游例程的两处关键增强，也是理解"为什么浏览器要显示接听/拒接按钮"的核心。

```text
start_webrtc():
   esp_webrtc_enable_peer_connection(handle, false)   // webrtc.c:1336
        → esp_webrtc 内部 pending_connect = true
   esp_webrtc_start()
        → 信令 start：起 HTTPS 服务器，on_ice_info()/on_connected() 被调用
        → signal_ice_received(): 看到 pending_connect → 只打印
             "Pending connection until user enable"，不建 PeerConnection
        → signal_connected(): no_auto_reconnect && pending_connect → 直接返回
             （否则会自动 esp_peer_new_connection 并发 offer）

浏览器点"接听" → ACCEPT_CALL → schedule_peer_connection_change(true)
   → 线程里 esp_webrtc_enable_peer_connection(handle, true)
        → pending_connect = false；signaling_connected 已为真
        → esp_peer_new_connection() → 板端生成 SDP → send_msg → SSE → 浏览器
```

**汇报话术**：*"官方例程是信令一连上就自动建连，也就是'设备永远在线可看'。门铃的语义相反——必须有人在门口按铃、由主人接听。所以我把自动重连关掉，改成由 ACCEPT_CALL 显式触发建连；这样板子不会在没人呼叫时一直被浏览器看着。"*

### 7.2.1 链路里两个"看起来矛盾"的地方，提前准备好解释

细读代码会发现两处与"局域网直连"叙事不完全一致的地方，评委如果较真会问：

1. **板端信令仍声明了一个公网 STUN 服务器**：
   `webrtc_http_server.c:477-480` 里 `ice_info` 的 `stun_url = "stun:stun.l.google.com:19302"`，同时 `is_initiator = true`（即 ICE 角色为 controlling）。
   **如何解释**：公网 STUN 只影响"服务器派生候选"的收集，局域网内真正连通靠的是主机候选；ICE 会在候选对里优先选可用的本地路径，所以它不会阻塞局域网建连。真正让接通变快的是浏览器侧 `iceServers: []`（不再等公网 STUN 回包）以及关闭浏览器本地上行采集。**如果下次迭代要彻底干净，可以把这里的 `stun_url` 置空**（`esp_webrtc` 在 `stun_url` 为空时会退回配置里的服务器列表，`components/esp_webrtc/src/esp_webrtc.c:646-650`）。

2. **`start_webrtc(char *url)` 的 `url` 参数实际没有被使用**：
   `signaling_cfg.signal_url = url`（`webrtc.c:1251`），但本项目用的是自研 HTTP 信令实现，服务器地址由板子自己决定，`url` 始终传 `NULL`。
   **如何解释**：这是保留下来的上游接口形态——上游示例用它指向公网信令服务器（AppRTC/Janus/KVS），本项目改成板内自建信令后，这个参数自然不再需要，保留是为了不破坏上游 API 形状。

### 7.3 `webrtc.c` 里的 4 把锁与 1 个状态机

| 锁 | 保护对象 | 出现位置 |
| --- | --- | --- |
| `door_bell_mutex` | `door_bell_state`、`webrtc` 句柄、工作线程开关 | 几乎每个函数 |
| `webrtc_api_mutex` | 对 `esp_webrtc_*` 的调用序列化 | `start/stop/request_ring/close_data_channel` |
| `webrtc_lifecycle_mutex` | `start_webrtc` / `stop_webrtc` 互斥，防止并发启停 | `webrtc.c:1183, 1431` |
| `data_channel_mutex` | `user_ch[]` 数据通道槽位 | `add/remove/clear_channel` |

状态机（`webrtc.c:48-54`）：

```text
NONE ──request_ring──► RINGING ──ACCEPT_CALL──► CONNECTING ──EVENT_CONNECTED──► CONNECTED
  ▲                       │                          │                             │
  │                       └──────DENY_CALL───────────┴────────DENY_CALL────────────┘
  │                                        ▼
  └──────── EVENTS(DISCONNECTED/CONNECT_FAILED) ── DISCONNECTING ──disable 成功──► NONE
```

三条防御性设计，值得单独讲：
1. **句柄校验**：`door_bell_change_state(source_handle, ...)` 只在 `webrtc == source_handle` 时才改状态（`:264-271`）。防止"上一次通话的旧事件"污染新会话。
2. **过渡态保护**：`DISCONNECTING` 期间收到 `CONNECTED` 会被忽略并打日志（`:266-268`），避免拆连接过程中又被拉回去。
3. **失败回滚**：`restore_peer_change_state_locked()`（`:275-288`）在"启停 PeerConnection 失败"时把状态退回原值；如果原状态是 `RINGING`，还会重新播放铃声，不让用户面对一个"既不响也没提示"的死状态。

### 7.4 数据通道：为什么代码里有一条"自测"通道

`webrtc.c:762-833` 的 `data_thread_hdlr` 每秒往 `channel1/channel2` 发一条 8 KB 字符串（`Send to <label> count N` + 重复填充字符），浏览器侧 `verify_data()`（`:842-859`）校验"填充字符是否等于计数的函数值"。用途是**数据通道可靠性自测**（丢包、重排、大消息分片），串口命令行 `close <idx>` 可以手动关通道复现异常。它不是门铃业务功能，汇报时一句话带过即可，**不要把它讲成"业务数据通道"**。

真正走数据通道以外路径的业务消息，全部走**信令的 customized 通道**（因为要保证在通话未建立时也能送达）。

### 7.5 RTP 变换器：一个调试钩子，不是功能

`webrtc.c:905-1050` 实现了发送/接收两侧的 RTP 包文本变换（在 RTP 载荷前后插入长度与 `TAIL_<n>` 标记），默认关闭，只能通过 `customized` 命令 `ENABLE_RTP_TRANSFORMER` 打开，浏览器侧还要开 `encodedInsertableStreams`。作用是在真实链路上验证"RTP 变换 API + 可插入流"能否工作（上游示例特性）。**汇报时如被问到，回答"这是上游提供的 RTP 变换能力验证，本作品的音视频不依赖它"。**

## 第 8 章 逐模块精读要点

### 8.1 `main.c`：装配者与事件汇合点

三个职责：
1. **装配**（`app_main`，见第 5 章）；
2. **线程策略**（`thread_scheduler` / `capture_scheduler`，见 5.3）；
3. **事件汇合**：把"雷达回调"和"视觉回调"这两个外来事件转成（a）SSE 消息、（b）融合输入、（c）来电请求。

关键实现细节：
- 融合器有自己的互斥锁 `sensor_fusion_mutex`，因为雷达回调（UART 任务）和视觉回调（AI 任务）是**两个不同线程**，都会改融合器状态（`main.c:56-84`、`:112-119`）。
- 启用 AI 时，雷达的响铃逻辑被替换：`#ifdef CONFIG_DOORBELL_SUPPORT_PEDESTRIAN_DETECT` 分支走融合，`#else` 分支保留"纯雷达直接响铃"（`main.c:198-212`）。这既方便对比，也保证关掉 AI 开关时功能不缺失。

### 8.2 `webrtc_http_server.c`：板上的"信令服务器"

**它本质上是一个 `esp_peer_signaling_impl_t` 实现**（`:596-604`）：`start` 建服务器和队列，`send_msg` 把板端消息塞进队列，`stop` 清理。

服务器参数（`:376-407`）：
- `httpd_ssl_config_t` + 内嵌自签名证书/私钥；
- `max_uri_handlers = 16`，`stack_size = 8192`；
- `max_open_sockets = 7`（默认 4 不够：页面 + SSE + 铃声 + 浏览器探测连接会挤满）；
- `lru_purge_enable = true`、收发超时 5 秒；
- 主动把 `esp-tls-mbedtls` / `esp_https_server` / `httpd` 日志降到 NONE，因为浏览器会发大量"预探测"TLS 连接，会产生刷屏的预期报错。

4 个 URI：

| URI | 方法 | 作用 |
| --- | --- | --- |
| `/webrtc/test` | GET | 下发内嵌的 `webrtc_test.html`（`text/html; charset=utf-8`） |
| `/webrtc/signal` | GET | **SSE 下行**：`text/event-stream`，板 → 浏览器 |
| `/webrtc/signal/post` | POST | **上行**：offer/answer/candidate/bye/customized |
| `/webrtc/ring.aac` | GET | 网页铃声文件（`Cache-Control` 一年） |

**SSE 的三条队列**（`:32-34`）：

| 队列 | 长度 | 语义 | 丢弃策略 |
| --- | --- | --- | --- |
| `signaling_queue` | 10 条 `char*` | SDP / candidate / bye / customized（信令本身） | 满则阻塞 100 ms 后丢并告警 |
| `telemetry_queue` | 16 条 256 B | 雷达事件等"必须看到"的事件 | 满则丢最旧一条 |
| `vision_queue` | **1 条** 1024 B | 最新视觉快照 | `xQueueOverwrite` 覆盖，永远只保留最新 |

**为什么视觉快照只留 1 条？** 视觉 2 FPS 持续产生数据，如果排队就会越积越久、画面上的框会严重滞后。所以设计成"只保留最新一帧状态"，用 `sequence` 号判断是否是新数据（`:74-92`、`:141-144`）。这是实时系统里很典型的"**丢旧保新**"策略。

**单会话 + 刷新替换**：全局只有一个 `event_stream`。新的 GET 进来时把旧的 `stopping = true`（`:185-190`），旧推送任务退出并释放，新页面立刻接管。这修掉了"刷新网页后第一次按 BOOT 没反应"的问题。

**心跳**：每 5 秒发 `{"type":"heartbeat"}`，写失败就认为对端消失并结束任务（`:158-166`）。

**自定义命令字表**（板→网页，`webrtc.c:26-39`；网页→板），完整清单：

| 方向 | 命令 | 含义 |
| --- | --- | --- |
| 板→网页 | `RING` / `RING_STOPPED` | 来电 / 铃声结束（4 秒后） |
| 板→网页 | `DOOR_OPENING` / `DOOR_OPENED` / `DOOR_CLOSING` / `DOOR_LOCKED` / `DOOR_FAILED` | 门锁状态回执 |
| 板→网页 | `CALL_ENDED` / `CALL_END_FAILED` | 挂断结果确认 |
| 板→网页 | `PEDESTRIAN_DETECTED` | **已停用**：检测回调配置为 NULL，实际视觉事件统一走 `vision_state` JSON（见第 13 章第 2 条） |
| 网页→板 | `ACCEPT_CALL` / `DENY_CALL` | 接听 / 拒接挂断 |
| 网页→板 | `OPEN_DOOR` | 开门 |
| 网页→板 | `ENABLE_RTP_TRANSFORMER` / `DISABLE_RTP_TRANSFORMER` | 调试开关 |

### 8.3 `media_sys.c`：把"设备"变成"媒体提供者"

`media_sys_buildup()` 做四件事（`:400-415`）：
1. 注册默认编解码器（`esp_video_enc/dec_register_default`、`esp_audio_enc/dec_register_default`）；
2. **预处理开门提示音**（`prepare_open_door_prompt`，`:152-250`）：读内嵌 `open.aac` → 解析 ADTS 头（采样率索引表在 `:131-134`）→ 逐帧 `adec_decode` → 重采样到 16 kHz 单声道 → 存进可增长的 PCM 缓冲；末尾 1 个 `0x00` 字节被容忍，其他残留字节视为错误；
3. 建采集系统（`:342-360`）：摄像头源（P4 走 `esp_video_init` + V4L2 `/dev/video0`，2 个缓冲）+ 麦克风源，同步模式 `ESP_CAPTURE_SYNC_MODE_AUDIO`；
4. 建播放系统（`:362-398`）：音频 render 用 `av_render_alloc_prompt_overlay()`（**这是本项目替换上游的关键点**），视频 render 用 LCD（**本板未接屏幕**：doorbell_local 中没有任何 `board_lcd_init()` 调用，`board_get_lcd_handle()` 返回 NULL，因此 `video_render == NULL`，日志会打印 `Video render not set, stream is skipped`，代码允许失败继续），FIFO 大小分别为音频 4 KB/6 KB、视频 500 KB。

`media_sys_get_provider()` 把这两个句柄交给 `esp_webrtc`（`webrtc.c:1265-1267`）。

另有三个"业务入口"：`play_music(data, size, duration)`（`:544`，起 `music_player` 线程播放 AAC，`duration>0` 表示限时循环）、`stop_music()`（`:564`，置标志并等线程退出）、`test_capture_to_player()`（`:424`，串口 `rec2play` 命令，本地环回自测采集与播放）。

### 8.3.1 语音数据的完整来回路径（双向音频怎么走）

| 方向 | 路径 |
| --- | --- |
| 上行（门口说话 → 浏览器） | 板载麦克风 → ES8311 ADC → `esp_capture` audio dev src（`media_sys.c:347-350`）→ G711A 编码（`aenc_0`）→ sink 0 → `esp_webrtc` 发送线程 → `esp_peer` 打包 SRTP → 浏览器 |
| 下行（浏览器说话 → 板载扬声器） | 浏览器 → SRTP → `esp_peer` → `esp_webrtc` 的 `pc_on_audio_data` → `av_render_add_audio_data` → G711A 解码 → **prompt overlay（可选混音）** → i2s_render → `esp_codec_dev_write` → ES8311 DAC → 扬声器 |

注意下行路径里 **prompt overlay 正好夹在"解码之后、写 I2S 之前"**——这就是为什么能在播报的同时不打断通话：它只是在那一段 PCM 上加了一次运算。提示音播放（`play_music`）走的是另一条完全独立的 AAC 解码链，两条链共用同一个 I2S 输出，所以同时开会有冲突，这也是提示音必须走 overlay 而不是 play_music 的原因。

### 8.4 `door_lock.c` / `door_lock_state.c`：执行器

- PWM：LEDC 低速模式、TIMER_3、CHANNEL_7、14 位分辨率、50 Hz、GPIO32（`door_lock.c:13-18`）；
- 脉宽 → 占空比换算 `pulse_us_to_duty()`（`:36-41`），开机即输出 500 μs（机械锁定位置）；
- 请求只入队（`door_lock_request_open()`），由独立 `door_lock_task` 顺序执行"开 → 保持 5 s → 关"（`:84-125`），**重复点击是幂等的**；
- 每次状态变化通过回调通知 `webrtc.c`，转成 customized 命令推给网页；
- 纯状态机在 `door_lock_state.c`（54 行、无硬件依赖），因此可以在 PC 上用 C 单元测试覆盖（`tests/door_lock_state_test.c`）。

**必须说清的边界**：舵机没有位置/电流反馈，`UNLOCKED` 只表示"命令已发出且动作时间已过"，**不能证明锁舌到位**。

### 8.5 `radar_ld2450.c` / `presence_fusion.c`：传感器

- 帧格式常量在 `radar_ld2450.h:11-17`（4 头 + 3×8 目标 + 2 尾 = 30 字节），串口参数在 `:22-24`（256000、GPIO4/5）；
- 解析器分三层：`ld2450_parse_frame`（单帧校验与解析）、`ld2450_stream_feed`（滑窗重同步，能吃任意分片和噪声）、`ld2450_should_capture_sample`（采样辅助）；
- `presence_fusion.c` 是纯逻辑：区域判定 `presence_fusion_target_in_zone()`、方向判定 `presence_fusion_classify_direction()`（带死区）、主状态机 `presence_fusion_process()`；
- 关键常量集中在 `presence_fusion_default_config()`：区域 X[-1500,1500]、Y[300,3000] mm，进入 1 s 确认，离开 2 s 确认，冷却 10 s。

### 8.5.1 板级适配：`board.c` + `board_cfg.txt` + `codec_init`

这一层是"复刻"的核心工作量之一，被问"你怎么把官方例程搬到这块板上的"时这样讲：

```text
init_board()                     (board.c:45-58)
  → set_codec_board_type("WT99P4C5_S1")      用板名去查板级表
  → codec_init_cfg_t cfg = { .reuse_dev = false }
  → init_codec(&cfg)                          配置 codec 芯片与 I2S
```

板级表 `components/codec_board/board_cfg.txt:81-95` 里 WT99P4C5_S1 段的关键信息：

| 项 | 值 | 含义 |
| --- | --- | --- |
| `i2c` | SDA 7 / SCL 8 | 控制 ES8311 的 I2C 总线 |
| `i2s` | mclk 13 / bclk 12 / ws 10 / dout 9 / din 11 | 音频数据引脚 |
| `in_out` | codec `ES8311`，pa 53，use_mclk 1，pa_gain 6 | **单颗 ES8311 同时做 DAC 与 ADC**（不是"ES8311 + ES7210"这种双芯片方案） |
| `camera` | `type: mipi` | 走 MIPI-CSI（OV5647） |

`reuse_dev = false`（`board.c:50`）的含义：**播放和录音使用两套独立的 `esp_codec_dev` 句柄**，因此可以分别用不同采样率（`codec_init.c:478-486`）——这对"通话 16 kHz + 提示音 16 kHz + 铃声 44.1 kHz"的混合场景是必要的。

三个预录提示音的实际参数（由 AAC 头解析得到）：

| 文件 | 采样率 | 声道 | 时长 | 用途 |
| --- | --- | --- | --- | --- |
| `ring.aac` | 44.1 kHz | 单声道 | 约 1.23 s | 板端来电铃声（循环到 4000 ms） |
| `open.aac` | 24 kHz | 单声道 | 约 2.99 s | 开门播报（预解码为 16 kHz PCM） |
| `join.aac` | 16 kHz | 单声道 | 约 2.05 s | 启动/接通提示音 |

### 8.8 三个"纯逻辑小模块"的重要性

`door_lock_state.c`(54) + `doorbell_ring_policy.c`(29) + `multimodal_fusion.c`(82) = 165 行，却承担了门锁、来电准入、自动触发三个关键决策。它们被刻意写成**不依赖硬件、不依赖 FreeRTOS** 的纯函数，所以能用宿主机测试（不需要烧板）覆盖。**这是本项目的测试策略核心，汇报时值得作为一个"工程方法"亮点讲。**

### 8.9 一个必须如实说明的点：`doorbell_status.c` 目前没有接线

`doorbell_status.h/.c` 定义了一套统一状态快照（在场/通话/门锁/网络/两个模型状态），但：
- 生产代码中**没有调用** `doorbell_status_init()` / `doorbell_status_apply_vision()`；
- 网页上的状态显示实际来自 SSE 的 `vision_state` 和 `radar_event`，以及 `customized` 命令字（`DOOR_OPENING`、`CALL_ENDED` 等）；
- 结构体里的 `call` / `lock` / `network` 字段除初值外从未被赋值，也没有 JSON 序列化函数。

**汇报建议**：把它讲成"**预留的统一状态聚合模块**，目前已实现并有单元测试，下一步用于给网页提供一条 `{"type":"status"}` 总状态事件"。**不要说"网页状态由 doorbell_status 统一提供"**，那与代码不符——评委只要搜一次函数名就能发现。

**四道超时兜底**（这是前端健壮性的核心，被追问"网络不好会怎样"时用）：

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `RING_FALLBACK_TIMEOUT_MS` | 4500 ms | 即使没收到 `RING_STOPPED` 也会停铃，避免无限响 |
| `PEDESTRIAN_EPISODE_TIMEOUT_MS` | 3000 ms | 一次"行人出现"事件的持续窗口，避免单帧把状态一直挂在"有人" |
| `VISION_STATE_STALE_MS` | 3000 ms | 超过后把检测框标记为过期并清空叠加层 |
| `HANGUP_ACK_TIMEOUT_MS` | 8000 ms | 没等到 `CALL_ENDED` 就提示"开发板无法结束通话，请重试"，不清状态 |
| `DISCONNECT_GRACE_PERIOD_MS` | 15000 ms | ICE 短暂 `disconnected` 不主动挂断 |

**一个容易被忽略的细节**：视频用 `object-fit: contain` 显示，所以画面两侧可能有黑边；检测框坐标必须按 letterbox 后的实际显示区域换算，否则框会整体偏移（`webrtc_test.html:700-708`）。这说明前端不只是"画个矩形"。

**候选早到的竞态处理**：如果远端 candidate 比 offer 先到，前端会先缓存，等 `handleOffer` 时再补放（`webrtc_test.html:1361-1365`、`:1266-1280`）。这是 WebRTC 里非常经典的时序坑。

## 第 9 章 配置层：为什么改这些数字就能适配硬件

配置分四层，从"改代码"到"改菜单"，逐层收敛：

```text
① 应用级常量        main/settings.h                      板名、分辨率、帧率、GPIO、Wi-Fi 引入
② 功能开关          main/Kconfig                          CONFIG_DOORBELL_SUPPORT_PEDESTRIAN_DETECT
③ 工程默认配置      sdkconfig.defaults / .esp32p4         Flash、PSRAM、芯片 revision、摄像头、C5 SDIO、模型
④ 板级引脚表        components/codec_board/board_cfg.txt I2C/I2S/PA/摄像头/屏幕
⑤ 依赖与版本        main/idf_component.yml                AI 模型、esp_hosted、esp_wifi_remote、本地组件
```

关键项解释（汇报被问到能立刻答）：

| 配置 | 值 | 为什么 |
| --- | --- | --- |
| `CONFIG_ESP32P4_SELECTS_REV_LESS_V3` / `REV_MIN_100` | y | 实测板子是 P4 rev 1.3，不这样设会拒绝烧录 |
| `CONFIG_ESPTOOLPY_FLASHSIZE_16MB` | 16 MB | 板载 16 MB Flash；应用分区 8 MB |
| `CONFIG_SPIRAM_SPEED_200M` | 200 MHz | 32 MB PSRAM 用于帧缓冲、线程栈、模型 |
| `CONFIG_ESP_HOSTED_IDF_SLAVE_TARGET="esp32c5"` + SDIO 引脚 | C5 | P4 无 Wi-Fi，Wi-Fi 由板载 C5 通过 SDIO 提供 |
| `CONFIG_WIFI_RMT_*` 一组 | 固定值 | 锁定 esp_wifi_remote 1.6.3 的缓冲区契约，使干净构建不依赖旧 sdkconfig |
| `CONFIG_WIFI_RMT_NVS_ENABLED=n` | 关 | 始终用应用提供的凭据，避免 C5 里的旧 NVS 覆盖 |
| `CONFIG_CAMERA_OV5647=y` + RAW10 1280×960 binning | OV5647 | 板载 MIPI-CSI 摄像头；ISP 管线打开 |
| `CONFIG_DOORBELL_SUPPORT_PEDESTRIAN_DETECT=y` | 开 | 启用 AI 支路（同时决定 C++ 源文件是否参与编译） |
| `CONFIG_HUMAN_FACE_DETECT_MSRMNP_S8_V1` + `MODEL_IN_FLASH_RODATA` | y | 人脸存在模型量化版本与放置位置 |
| `partitions.csv`：`nvs 0x5000 / phy 0x1000 / factory 0x800000 / pedestrian_det 500K` | — | 8 MB 应用分区给固件（当前约占 82%），500K 给模型 |

`main/idf_component.yml` 里两处细节值得讲：
- `override_path: ../../../components/...` 表示**优先用仓库内组件而不是组件仓库版本**——保证提交快照自洽；
- `espressif/esp_hosted: 2.12.12` 与 `esp_wifi_remote: 1.6.3` **精确锁版本**，因为不锁定的话干净环境会解析到 Kconfig 契约不同的新版本，导致"我机器上能构建、评审机器上不能"。

## 第 11 章 汇报速查

### 11.1 一分钟总述（背下来）

> 这是一个跑在 WT99P4C5-S1 上的局域网 WebRTC 智能门铃，基于 Espressif 官方 `doorbell_local` 例程做的硬件移植与功能扩展。P4 负责音视频和 AI，板载 C5 通过 SDIO 提供 Wi-Fi。板子自己就是 HTTPS 服务器：它下发中文网页、用 SSE 向网页推事件、用 POST 接收网页命令，音视频走 WebRTC 直连，局域网内不依赖外部服务，实测接通约 4～6 秒。功能上，BOOT 按键、LD2450 毫米波雷达和摄像头人员检测三个来源汇入同一个来电入口；雷达判断"门前 3 米内有人进入"，摄像头判断"确实是人"，两个证据在 2 秒窗口内都成立才自动按铃，同一次来访只响一次。网页可以接听、看到板载 H.264 视频和双向语音、点击开门——开门通过 GPIO32 的 50 Hz PWM 驱动舵机模拟门锁，开门播报在启动时就被预解码成 PCM，并挂在通话音频的同一条输出路径上，因此不会像早期版本那样只能在挂断后播放。核心决策逻辑都写成了可在 PC 上做单元测试的纯函数，提交前 12 个自动检查全部通过，干净构建 1850 步完成，固件约 6.56 MiB、分区余 18%。

## 第 12 章 评委可能追问的 30 个问题（含答法）

### A. 架构与选型

1. **为什么不用 WebSocket 而用 SSE + POST？**
   SSE 是浏览器原生 API，服务端只需在 HTTP handler 里持续 `send_chunk`，实现量极小；上行频率很低（几次握手 + 少量命令），POST 足够。整套方案在 ESP32 上比引入 WebSocket 更省内存和代码量。而且**媒体不需要 WebRTC 之外的信令通道**，信令只要"能可靠送几条 JSON"。

2. **为什么板子自己当信令服务器？**
   局域网门铃的目标是"插上电、打开网页就能用"，不依赖任何外部服务；板子已有 Wi-Fi 和 HTTPS 能力，加一个信令实现只用了 604 行。

3. **为什么局域网不需要 STUN/TURN？**
   浏览器和板子在同一个二层网络，主机候选（host candidate）就能直连。浏览器侧配置 `iceServers: []`，服务端也不等待公网 STUN 响应——这是接通时间从约 30 秒降到 4～6 秒的主要原因之一。

4. **P4 和 C5 是怎么分工的？**
   P4 是主控：跑应用、音视频编解码、AI 推理、HTTPS 服务；它没有 Wi-Fi 射频。板载 C5 作为协处理器通过四线 SDIO 提供 Wi-Fi，由 `esp_hosted` + `esp_wifi_remote` 把 P4 上的 `esp_wifi_*` 调用转发到 C5。

5. **为什么要锁 `esp_hosted` / `esp_wifi_remote` 的版本？**
   这两个组件的 Kconfig 契约在版本间变化过，不锁定会导致"我的机器能构建、评审环境不能"。锁定后再把远程 Wi-Fi 缓冲参数写进 `sdkconfig.defaults.esp32p4`，干净构建就与本地一致。

### B. WebRTC 与媒体

6. **`no_auto_reconnect` 解决什么问题？**
   关掉"信令一连上就自动建连"，让建连必须由 `ACCEPT_CALL` 显式触发。门铃语义是"有人按铃、主人接听"，而不是"设备一直在线可看"。

7. **为什么摄像头采集不随挂断关闭？**
   `esp_webrtc_set_no_auto_capture(true)`（`webrtc.c:1271`）。P4 上重建 MJPEG/H.264 采集管线较慢，每次挂断都重建会让后续通话的视频明显晚到。保持常驻后，多轮通话视频都能及时出现。

8. **音频用什么编码？**
   默认 G711A 8 kHz 单声道（`WEBRTC_SUPPORT_OPUS` 未开启时）；代码里保留了 OPUS 16 kHz 双声道分支及其 40 KB 栈的线程配置。

9. **视频方向和音频方向？**
   视频 `SEND_ONLY`（板 → 浏览器），音频 `SEND_RECV`（双向）。浏览器端不需要上传摄像头，这也缩短了建连时间。

10. **通话中开门提示音为什么不打断通话？**
    因为它没有新开音频流，而是在自定义 audio render 的 `write` 回调里，把预先离线解码好的 16 kHz 单声道 PCM 加到输出 PCM 上并做 16 位饱和限幅（`doorbell_audio_render.c:147-175` + `pcm_overlay.c`）；远端长时间静音时由后备线程输出承载提示音的帧（`:38-97`）。
    **追问"那 8 kHz 的 G711A 怎么办"时**：如实回答——overlay 的混音分支要求 16000 Hz（`:134-137`），默认 G711A 构建下走的是"静音间隙 + 后备线程"路径；若要稳定混音，需要启用 OPUS（16000 Hz）或扩展重采样逻辑。这是已知的配置耦合点。

11. **提示音为什么要预解码？**
    通话时再做 AAC 解码会引入延迟和抖动，而且解码与混音在同一路径上更容易卡顿。启动时一次性解码 + 重采样成 16 kHz 单声道常驻内存，通话中只做加法。

12. **数据通道做什么用？**
    主要作为可靠性自测（每秒 8 KB 大消息 + 校验），业务命令走信令的 `customized` 消息，因为要保证通话未建立时也能送达。

13. **RTP Transformer 是功能吗？**
    不是，是上游的 RTP 变换 API 验证钩子，默认关闭，本作品音视频不依赖它。

### C. 感知与算法

14. **雷达凭什么判断"进入"？**
    30 字节帧解析出最多 3 个目标的 X/Y/速度；先做门前区域判定（X ±1500 mm、Y 300～3000 mm），再用状态机去抖：连续 1 秒在区内才算"进入确认"，连续 2 秒不在区内才算"离开确认"，离开后 10 秒冷却。

15. **为什么用"区域 + 去抖"而不是直接按距离阈值？**
    人在门口来回走动、雷达噪声都会让瞬时判定抖动；时间维度的确认把误触发压下去，冷却则防止徘徊反复响铃。

16. **视觉为什么有两个模型？**
    行人模型是主判据；人脸存在模型作为近距离辅助证据——当雷达正关注门前、或者没有可信行人框时也会跑人脸，避免"人贴得很近只露脸"这种漏检。

17. **为什么检测支路是 320×180@2 FPS？**
    独立于 640×480@15 FPS 的通话视频。低分辨率低帧率把 AI 开销控制住（约占 17% CPU），不抢通话的实时性；推理明显变慢时还会自动降帧保护通话。

18. **"4 帧命中 3 帧"是什么？**
    视觉跟踪器的确认条件：在滑动窗口内命中达到阈值才把目标标为 confirmed，连续丢失若干帧才清除；同时做 IOU 关联并避免"人体框内的人脸"被重复计数。

19. **双证据融合的具体条件？**
    雷达在区内、该次进入允许响铃、本次来访尚未响过、且 2 秒内存在视觉证据（行人优先，人脸次之）。四条同时成立才请求来电；雷达离开时清空"本次来访"标记。

20. **这套机制能保证不误报吗？**
    不能保证。它的作用是**显著降低**单传感器误触发：雷达会被门外经过的物体触发，视觉受光线和角度影响。真实边界是"两个独立证据同时成立"，不是"无误报"。

### D. 执行器与硬件

21. **舵机参数与动作流程？**
    GPIO32、50 Hz、500 μs 锁定、2500 μs 打开；动作流程为 LOCKED → OPENING（500 ms 裕量）→ UNLOCKED（保持 5 s）→ CLOSING（500 ms）→ LOCKED。请求只入队，由独立任务顺序执行，重复点击幂等。

22. **怎么知道门真的开了？**
    不知道。舵机没有位置、电流或限位反馈，`UNLOCKED` 只表示命令执行且动作时间已过。真实到位反馈需要限位开关或电流检测，属于后续工作。

23. **舵机供电怎么处理？**
    舵机用独立稳压 5 V 供电，与主板只共地，不并联 5 V；雷达单独分支走线。原因是舵机堵转电流约 1 A，共电源会拉低电压导致雷达串口乱码或主板复位（`docs/bringup/servo-power-and-safety.md`）。

24. **雷达接线与串口参数？**
    UART1、256000 8N1，RX=GPIO4、TX=GPIO5，5 V 供电，与舵机分开供电分支。

### E. 工程与质量

25. **怎么保证 AI 不会拖垮系统？**
    三层保护：独立低分辨率低帧率支路、`thread_scheduler` 给 `detect` 线程 24 KB 栈并降优先级、推理过慢时自动降帧。此前的真实故障就是检测线程 4 KB 栈 + 浮点格式化触发栈保护重启，提高栈并改静态 JSON 缓存后连续观察约 7 分钟无异常。

26. **为什么这么多模块写成纯函数？**
    为了可测试。门锁状态机、来电策略、融合决策、雷达存在状态机、PCM 混音都不依赖硬件和 RTOS，可以在 PC 上编译运行单元测试，覆盖各种状态组合。

27. **测试覆盖了什么？怎么跑的？**
    14 个 Python 检查脚本 + 13 个宿主机 C 单元测试。前者既校验源码契约（网页、板级配置、接线），也会编译并运行后者。提交前实测 14/14 通过，C 测试 13/13 全部被覆盖。

28. **内存和性能余量？**
    应用分区 8 MB，固件 `0x68fd20`（约 6.56 MiB），余 18%；AI 检测约占 17% CPU，双核空闲约 77% 与 98%；检测线程剩余栈约 21 KB。

29. **页面刷新后第一次按 BOOT 会丢来电吗？**
    不会。新建立的 SSE 连接会立刻把旧的标记为停止并接管，避免旧连接占着事件通道；这也是调试中修掉的问题之一。

30. **按了挂断但视频还在播怎么办？**
    现在的实现是"确认式挂断"：网页发 DENY_CALL 后不立即清状态，等板端回 `CALL_ENDED`（或失败时 `CALL_END_FAILED`）才关闭 PeerConnection、停麦克风、清空 `<video>`。以板端确认为唯一结束条件，保证界面与媒体一致。短暂断线另有 15 秒宽限，避免 Wi-Fi 抖动误挂断。

## 附录 A：术语速查

| 术语 | 在本项目里的含义 |
| --- | --- |
| SSE | 服务器发送事件，板 → 浏览器的一条长 HTTP 连接，用来推 JSON |
| 信令（signaling） | 交换 SDP 与 ICE 候选的过程；本项目由板端 HTTPS 服务器承担 |
| SDP | 会话描述：编码格式、方向、ICE 参数 |
| ICE / candidate | 打洞与候选地址；局域网内主要是主机候选 |
| DTLS / SRTP | 加密传输与加密媒体 |
| SCTP / data channel | WebRTC 的数据通道 |
| sink | `esp_capture` 的输出端；本项目用 sink 0 出 H.264 通话流、sink 1 出 RGB565 检测流 |
