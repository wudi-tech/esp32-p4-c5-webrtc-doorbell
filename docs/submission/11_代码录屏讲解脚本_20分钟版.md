## 一、这一版比旧版讲清了什么

旧版（10 分钟）的问题是"每个模块都点到了，但没讲透因果"：观众知道有哪些文件，却不知道为什么代码要写成这样。这一版的改动：

1. **先立骨架再进代码**：开场用 2 分钟建立"五层架构 + 三条通道"，后面每个模块都能挂到骨架上。
2. **每条链路讲三件事**：触发 → 处理 → 结果，并且明确说出"为什么必须这样写"（防重入、防竞态、防误触发）。
3. **加入现场运行画面**：不只是读代码，还展示网页来电、接听、视频、开门、断线恢复，让"代码 → 现象"的对应关系看得见。
4. **主动交代边界**：把"未实现 / 有限制 / 待复测"的内容集中讲清（第 9 段），比被追问更可信。
5. **每段都有"评委验收点"**：录完自查，确保该段想说的事真的说到了。

## 三、逐句台词与画面

### 第 1 段（0:00–2:00）项目定位、五层架构、三条通道

**画面**
1. 打开资源管理器，让左侧目录树同时出现 `components`、`solutions`、`docs`，停 3 秒。
2. 侧边打开 `10_代码结构从0讲清.md` 的第 3 章分层图（或用你准备好的架构图）。
3. 讲三条通道时，用手指/鼠标依次划过"网页 → 板""板 → 网页""浏览器 ⇄ 板"三条箭头。

**我说**

> 大家好，我是吴迪。这个作品是"ESP32-P4 加 C5 的多模态 WebRTC 智能门铃"，它复刻自乐鑫官方的 `esp-webrtc-solution` 仓库，具体基线是里面的本地门铃示例 `doorbell_local`。
>
> 先说清楚复刻和原创的边界。整个仓库里，`components` 目录是乐鑫的通用组件，`solutions` 下还有十一个其他示例，都不是我写的。我的作品集中在 `solutions/doorbell_local`，业务代码全在它下面的 `main` 目录里，一共二十二个源文件，加上一个中文网页、三段提示音和两个证书。
>
> 从整体上看，这个系统可以分成五层。最底下是硬件：P4 主控、板载 C5 无线芯片、OV5647 摄像头、ES8311 音频芯片、LD2450 毫米波雷达和一颗模拟门锁的舵机。往上是 ESP-IDF 提供的驱动和协议栈。再往上是乐鑫的能力组件，包括 WebRTC、Peer 协议栈、采集和渲染管线。第四层就是我写的业务逻辑，也是今天讲解的重点。最上面是浏览器里的中文网页。
>
> 这一层结构里最容易讲错的是通信：网页和板子之间其实有**三条完全不同的通道**。第一条是下行，板子到网页，用的是 SSE，也就是服务器推送事件，一条 `GET /webrtc/signal` 长连接，板子主动往里推 JSON。第二条是上行，网页到板子，用的是普通的 HTTP POST。第三条才是音视频本身，走 WebRTC，也就是 UDP 上的加密媒体流，它完全不经过 HTTP。很多人以为这里用了 WebSocket，其实没有——网页和板子之间是"轻量信令"，重媒体交给 WebRTC。

**评委验收点**：复刻基线说清了；五层架构说清了；三条通道没有混。

**画面**

3. 打开 `components/codec_board/board_cfg.txt`，框选 81～86 行。
4. 打开 `sdkconfig.defaults.esp32p4`，框选 10～13、17～23、25～35、44～49 行。
5. 打开 `main/idf_component.yml`，框选 7～33 行。

**我说**

> 先看工程入口。`main/CMakeLists.txt` 第 2 到第 7 行登记了所有业务源文件，舵机、雷达、音频、视觉都在里面；第 9 到第 11 行是条件编译，只有打开"行人检测"开关时，C++ 的检测文件才会参与编译；第 14 到 15 行把三段 AAC 提示音、中文网页和 HTTPS 证书直接嵌进固件。也就是说，这个设备没有文件系统，网页和音效都在固件的只读数据段里。
>
> 再看配置。`settings.h` 是应用级常量：第 21 到 25 行按芯片型号选择板名，P4 用 `WT99P4C5_S1`；第 30 到 38 行定义通话视频是 640 乘 480、15 帧；第 40 到 50 行定义独立的 AI 检测支路是 320 乘 180、2 帧，比通话支路低得多，这是为了把推理开销压住；第 56 到 61 行把 Wi-Fi 密码隔离到被 Git 忽略的 `settings.local.h`；第 76 行定义 BOOT 按键是 GPIO35。
>
> 板级引脚不写在业务代码里，而是写在一张板级表里。`board_cfg.txt` 第 81 到 86 行就是这块板：I2C 用 7 和 8 控制音频芯片，I2S 用 13、12、10、9、11 传音频数据，音频芯片是单颗 ES8311，它同时负责播放和录音，功放使能是 GPIO53。
>
> 最后是芯片级配置和依赖。`sdkconfig.defaults.esp32p4` 里，第 10 到 13 行锁定了 P4 的芯片版本，因为实测板子是 revision 1.3；第 17 到 23 行配置 OV5647 摄像头并打开 ISP 图像处理管线；第 25 到 35 行是最关键的一条：**P4 本身没有 Wi-Fi**，它通过四线 SDIO 连接到板载的 ESP32-C5，由 C5 提供无线能力，这套"主机加协处理器"的方案由 `esp_hosted` 和 `esp_wifi_remote` 两个组件支撑。第 44 到 49 行打开行人检测，并指定人脸存在模型的量化版本。`idf_component.yml` 第 7 到 33 行则把这些依赖的版本**精确锁定**，比如 `esp_hosted 2.12.12`，这样评审在干净环境里也能构建出同样的固件。

**评委验收点**：说明白"网页在固件里"；说明白 P4 无 Wi-Fi、靠 C5；说明白版本锁定的原因。

### 第 3 段（4:00–6:00）系统启动与线程/栈策略

**画面**
1. 打开 `main/main.c`，框选 435～479 行的 `app_main`，逐段高亮。
2. 框选 216～222 行的 `RUN_ASYNC` 宏。
3. 框选 361～395 行的 `thread_scheduler`，重点 380～391 行。
4. 框选 397～409 行的 `capture_scheduler`。
5. 打开串口日志，指一下启动时依次出现的板级、雷达、媒体、Wi-Fi、HTTPS 日志（提前滚好）。

**我说**

> 程序从 `main.c` 第 435 行的 `app_main` 进入。这四十多行的顺序本身就是设计。
>
> 第 438 到 440 行先注册媒体适配层和两套线程策略；第 441 行初始化板级音频；接着第 442 行是 `doorbell_webrtc_init`，它只做一件事——创建四把互斥锁。**为什么必须放在雷达和按键之前？** 因为这些外设一旦初始化，回调就可能立刻触发，而所有来电请求都要用这几把锁。先有锁、后有回调，才不会出现"回调已经来了、同步对象还是空的"这种竞态。
>
> 第 446 到 454 行初始化多模态融合器和它自己的锁；第 455 行初始化舵机 PWM；第 460 到 471 行初始化雷达存在状态机并启动 LD2450 的串口任务；第 472 行构建媒体系统；第 473 行起串口命令行；第 474 行初始化 Wi-Fi。最后是一个两秒一次的循环，用来查询 WebRTC 状态。
>
> Wi-Fi 拿到 IP 之后会回调第 420 行的 `network_event_handler`。注意这里没有直接调用启动函数，而是用 `RUN_ASYNC` 宏在**新线程**里启动 WebRTC——也就是第 216 到 222 行这个宏。原因很简单：启动过程要建 HTTPS 服务器、开 WebRTC、等锁，耗时较长，如果直接在 Wi-Fi 事件任务里做，会影响协议栈。
>
> 第 361 行的 `thread_scheduler` 是所有线程的"资源分配表"，它按线程名给每个任务定制栈大小、优先级和绑定的核心。这里讲两个真实的教训。第一，第 380 到 382 行给 AI 检测线程 `detect` 分配 24 KB 栈、优先级降到 8。之前这个线程只有 4 KB 栈，浮点格式化触发了栈保护重启，表现是网页卡顿、按键失效；加大栈并把 JSON 改成静态缓存之后，连续观察七分钟没有异常。第二，第 384 到 388 行把 PeerConnection 的主任务 `pc_task` 放到核心 1、25 KB 栈，避开核心 0 上的媒体管线。
>
> 第 397 行的 `capture_scheduler` 做了一件小事但很重要：把采集线程的栈标记成"分配在外部 PSRAM"。P4 的片内 RAM 有限，只有把栈放到 32 MB 的 PSRAM 里，才能同时开这么多任务。

**评委验收点**：初始化顺序的理由说清了；栈故障的真实故事讲出来了；"栈放 PSRAM"讲到了。

### 第 4 段（6:00–7:40）统一来电入口与 BOOT 按键

**画面**
1. `webrtc.c` 框选 1091～1126 行的 `key_monitor_thread`，指 1105～1121 行。
2. 框选 333～405 行的 `doorbell_request_ring`，分三次框选：346～356、357～371、373～396。
3. 框选 290～331 行的 `ring_stop_worker` 与 `schedule_ring_stop`。
4. 框选 `doorbell_ring_policy.c` 全文（29 行）。
5. 现场：按一下板上 BOOT 键，网页出现来电界面、板端响铃；4 秒后网页铃声停止。

**我说**

> 门铃的来电有三个来源：板上 BOOT 按键、LD2450 雷达、以及"雷达加摄像头"的融合结果。这段代码最重要的设计是：**三个来源全部汇入同一个入口**，也就是第 333 行的 `doorbell_request_ring`。
>
> 先看 BOOT。第 1091 行的任务在初始化时先记下按键的**启动电平**，然后每 50 毫秒读一次；只有当电平相对启动电平发生变化时才算一次按铃，然后调用统一入口。这个"以启动电平为基准"的写法，解决了按键上电悬空或长按导致的误触发。
>
> 再看统一入口。第 346 到 356 行在锁内做两件事：判断策略，并把状态**预占**成 `RINGING`，同时把铃声代次 `ring_generation` 加一。第 357 到 371 行如果策略不允许，就直接返回并打日志，告诉我们是被"未就绪"还是"忙"拒绝——这就是防重复呼叫的实现，而不是靠延时去抖。
>
> 第 373 行把 `RING` 命令通过信令发给浏览器，第 387 行让板子自己播放铃声。**为什么要有代次？** 因为第 393 行起了一个 4 秒后执行的线程来通知网页停止铃声。如果这 4 秒内用户挂断又重新来电，旧线程不能把新铃声关掉，所以第 298 到 300 行会核对代次，代次不对就不发。
>
> 这里还要说清一件事：板端响铃和网页响铃是**两套**。板子播的是内嵌的 `ring.aac`，网页播的是通过 HTTPS 下发的同一个文件；`RING_STOPPED` 是两者同步的握手，网页另外有 4.5 秒超时兜底，避免异常情况下一直响。
>
> 策略本身被单独抽成 29 行的纯函数，第 3 到 12 行：WebRTC 没准备好返回"未就绪"，门铃不是空闲返回"忙"，否则接受。因为它不依赖任何硬件和操作系统，所以可以直接在电脑上做单元测试——这是本项目的一贯做法：**把决策逻辑从硬件里挤出来，让它可测**。

**评委验收点**：多来源单入口讲清了；防重入与铃声代次讲清了；纯函数可测的设计意图讲到了。

### 第 5 段（7:40–9:40）板端信令服务：页面、SSE、POST

**画面**
1. `webrtc_http_server.c` 框选 376～407 行的服务器参数。
2. 框选 410～440 行的四个 URI 注册。
3. 框选 178～211 行的 SSE 注册函数，重点 185～203 行。
4. 框选 107～175 行的推送任务，重点 116～157 行；再指 32～34 行的三个队列定义。
5. 框选 214～348 行的 POST 处理，重点 273～333 行的消息分类。
6. 框选 596～604 行，说明这就是交给 `esp_webrtc` 的信令实现。
7. 现场：浏览器 F12 打开网络面板，展示 `/webrtc/test`、`/webrtc/signal`（持续中）、`/webrtc/ring.aac`。

**我说**

> 板子上跑的这段代码，本质是一个"信令服务器"。它对外有四个地址：`/webrtc/test` 下发中文网页，`/webrtc/signal` 是 SSE 下行长连接，`/webrtc/signal/post` 是唯一的 HTTP 上行接口，`/webrtc/ring.aac` 给网页提供铃声文件。第 376 到 407 行是服务器初始化，其中第 382 行把并发连接数从默认的 4 提到 7，因为页面、SSE、铃声和浏览器的 TLS 探测会同时占用连接；第 389 到 391 行把 HTTP 和 TLS 日志静音，否则浏览器的预探测连接会把串口刷爆。证书是第 393 到 401 行内嵌的自签名证书。
>
> SSE 这段是核心。第 32 到 34 行定义了三条队列，丢弃策略各不相同，这是有意设计的：信令队列 10 条，装会话描述、候选和自定义命令，满了会丢并告警；遥测队列 16 条，装雷达事件这类必须让用户看到的消息，满了丢最旧的一条；视觉队列只有 1 条，用覆盖写永远只保留最新一帧。
>
> **为什么视觉只留一条？** 因为视觉是每秒两帧持续产生的，如果排队，网页上的检测框会比画面滞后好几秒。所以这里用"丢旧保新"，靠序号判断是否是新数据——这是实时系统里很典型的一种取舍。
>
> 第 185 到 190 行解决了一个真实故障：网页刷新时旧连接不一定会立刻断开，所以新连接一进来就把旧会话标记为停止，让它让位。之前的表现就是"刷新网页后第一次按 BOOT 没有来电"。第 158 到 166 行每 5 秒发一次心跳，写失败就认为对端已离开并结束任务，避免僵尸连接占内存。
>
> 上行只有一条路：第 214 行的 POST 处理。第 257 行解析 JSON，第 273 到 333 行按类型分发：`offer`、`answer`、`candidate`、`bye` 是 WebRTC 信令，`customized` 是我们自己的业务命令，比如开门、接听、挂断；第 294 到 311 行还会在收到 answer 时把 SDP 里的候选地址逐行抠出来单独投递，避免候选丢失。
>
> 最后看第 596 到 604 行——这个接口只有 `start`、`send_msg`、`stop` 三个函数。它就是把这整套 HTTP 服务器"伪装"成 WebRTC 框架期望的信令实现，在启动时注入进去。所以本项目没有额外的信令服务器进程，板子自己就是服务器。

**评委验收点**：三条通道的落点都在代码里指到了；三条队列的不同丢弃策略讲清了；"板子自己就是信令服务器"讲清了。

### 第 6 段（9:40–11:20）WebRTC 建连：为什么必须点"接听"

**画面**
1. `webrtc.c` 框选 1218～1255 行的配置结构，逐一指 1220～1238、1239～1246、1250～1254。
2. 框选 1336 行、1265～1271 行。

6. 现场：浏览器点"接听"，展示视频出现与计时；口述实测接通 4～6 秒。

**我说**

> 现在讲通话建立。`start_webrtc` 从第 1171 行开始，第 1218 到 1255 行是这个通话的全部参数：音频是 G711A、8 kHz、单声道，配置里保留了 OPUS 16 kHz 的分支；视频是 H.264、640 乘 480、15 帧。方向很关键：第 1237 行音频收发双向，也就是双向对讲；第 1238 行视频只发，板子到浏览器单向，浏览器不需要上传画面——这两条让建连更快也更省带宽。

> 第 1239 行注册浏览器命令回调，第 1241 到 1243 行注册数据通道回调。第 1246 行有一个关键开关：`no_auto_reconnect` 设为真，注释写得很清楚——信令一连上**不要**自动建立对等连接。
>
> **这就是门铃和普通监控摄像头的区别。** 普通例程是"设备一直在线、随时可看"；门铃是"有人按铃、主人接听"。所以第 1336 行先显式关掉对等连接，系统停在"信令已连接、媒体未建立"的状态，浏览器上才会出现接听和拒接按钮。
>
> 真正的建立发生在点接听之后。第 586 到 600 行收到 `ACCEPT_CALL`，把状态改成连接中，然后**另起线程**启用对等连接；第 495 行调用框架接口后，板子才产生自己的会话描述并通过 SSE 发给浏览器，随后双方交换网络候选、建立加密媒体通道。本机实测这个过程是四到六秒。
>
> 第 1265 到 1271 行是另一个提速细节：把媒体提供者交给框架后，第 1271 行开启"不自动采集"，摄像头采集管线在整个运行期保持常驻、不随挂断关闭。因为 P4 上重建视频管线较慢，每通电话都重建会让后续通话的视频明显晚到。第 1273 到 1328 行则在同一个采集系统上再挂一个 sink，输出 320 乘 180 图像给检测模型，与通话视频互不干扰。
>
> 第 1052 到 1082 行是连接状态回调，有两个防御性写法：只有连接成功才把状态改成已连接；处理配对事件前先核对该事件是不是来自当前这个会话句柄，如果是上一次通话残留的事件就直接忽略。实时系统里，"旧事件污染新会话"是最难查的一类 bug。

**评委验收点**：`no_auto_reconnect` 与门铃语义的关系讲清了；双向音频/单向视频讲清了；采集常驻的理由讲清了。

### 第 7 段（11:20–13:20）通话挂断与状态一致性

**画面**
1. `webrtc.c` 框选 477～533 行的 `peer_connection_change_worker`，重点 494～526 行。
2. 框选 601～619 行的拒接/挂断分支。
3. 框选 245～288 行的状态切换与回滚。

6. 现场：点"挂断"，展示状态栏先显示正在挂断、随后变为结束；再演示刷新页面后仍可再次来电。

**我说**

> 挂断这段看起来简单，但它是本项目改动最多的地方，因为它直接决定"界面和媒体是否一致"。
>
> 浏览器的接听和挂断在第 601 到 619 行处理。收到挂断命令后，先把状态置为"正在断开"，再另起线程去关闭对等连接。第 494 到 526 行是那个线程：关闭成功就回 `CALL_ENDED`，失败就回 `CALL_END_FAILED`。
>
> 网页侧的写法是重点。`webrtc_test.html` 第 833 行的挂断函数发完命令后**不会立刻清空界面**，而是显示"正在挂断"，然后等板端确认；第 861 行的 `finalizeHangup` 才是真正关闭连接、停止本地麦克风、清空视频元素的地方。第 846 到 852 行还有一个 8 秒的确认超时，超时就提示"开发板无法结束通话，请重试"，并且**保留状态**不清空。
>
> 为什么绕这一圈？早期版本是网页一按挂断就自己清状态，结果出现过"页面显示通话已结束、但视频还在播放"。改成"以板端确认为唯一结束条件"以后，界面和媒体就不会各说各话。这是**状态一致性优先于响应速度**的取舍。
>
> 第 519 行还有一个 15 秒的断线宽限：ICE 短暂进入断开状态时，不主动挂断，等它自己恢复。家用 Wi-Fi 抖动很常见，没有这个宽限会频繁误挂断。
>
> 板端这边，第 245 到 288 行有两个保护：一是在"正在断开"期间如果收到"已连接"事件，直接忽略，防止拆连接的过程中又被拉回去；二是如果启停失败，状态会**回滚**到原来的值——如果原来是响铃中，还会把铃声重新播起来，不让用户面对一个"既不响也没提示"的死状态。

**评委验收点**：确认式挂断的动机讲清了；15 秒宽限讲清了；失败回滚讲到了。

### 第 8 段（13:20–15:10）舵机门锁与通话中语音提示

**画面**
1. `door_lock.h` 框选 10～15 行。
2. `door_lock.c` 框选 36～56 行（脉宽换算）、84～125 行（动作流程）。
3. 打开 `door_lock_state.c` 全文（54 行），指状态迁移表。
4. `webrtc.c` 框选 574～585 行的开门分支；框选 407～440 行的状态回执。
5. `media_sys.c` 框选 152～175 行（预解码）、`:544` 起 `play_music`（铃声路径）。
6. `doorbell_audio_render.c` 框选 147～175 行（写回调）、38～97 行（兜底线程）；`pcm_overlay.c` 框选 61～95 行（叠加与限幅）。
7. 现场：通话中点"开门"，展示舵机动作与网页的中文提示（"正在开门 / 门已打开 / 门已锁定"）。

**我说**

> 开门功能分两部分：执行机构和语音提示。
>
> 执行机构是舵机。`door_lock.h` 第 10 到 15 行是全部参数：GPIO32、50 赫兹 PWM、锁定位置 500 微秒、打开位置 2500 微秒、动作等待 500 毫秒、保持 5 秒。`door_lock.c` 第 36 到 41 行把微秒换算成 LEDC 的占空比计数值；第 84 到 125 行是动作流程：打开、等 500 毫秒、保持 5 秒、关闭，整个过程约六秒。
>
> 关键设计是**异步**：网页发来请求时只往队列里放一条命令就立刻返回，真正的动作由独立任务顺序执行。所以重复点击是幂等的，不会叠加动作，也不会阻塞网络回调。每次状态变化都通过回调上报，转成"正在开门""门已打开"这类命令推给网页，网页据此显示中文状态并禁用按钮。状态机本身在 `door_lock_state.c`，只有 54 行，不碰硬件，可以在电脑上做单元测试。**这里必须说清一个边界**：舵机没有位置或到位反馈，所以"已开锁"只代表命令已执行、动作时间已走完，**不能证明锁舌真的到位**。
>
> 语音提示是本项目比较费心的点。最初直接播放 `open.aac`，但音频输出是独占的：通话时远端声音正在写入，再开一路播放就会互相打断，结果是"开门语音只能在挂断后才听到"。
>
> 现在的做法分三步。第一，启动阶段就把 `open.aac` **离线解码**成 16 kHz 单声道 PCM 常驻内存，也就是 `media_sys.c` 第 152 到 175 行，自己解析 AAC 帧头、逐帧解码、重采样。第二，把音频渲染器包一层，在 `doorbell_audio_render.c` 里把提示 PCM 装进一个叠加器。第三，通话时每写一帧远端音频，先经过第 147 到 175 行的写回调，在 `pcm_overlay` 里做样本级相加并做 16 位饱和限幅，再交给真正的 I2S 输出；第 38 到 97 行还有兜底线程，远端长时间没声音时由它输出承载提示音的帧。
>
> **这里我要如实说明一个当前限制**：叠加器的混音分支要求音频是 16 kHz，而默认通话音频是 G711A 8 kHz，所以在这套默认配置下，开门语音不会经混音分支输出。这条路径需要在实机上复测，或者把提示音预处理目标改成 8 kHz、或者启用 16 kHz 音频编码。**因此请不要把"通话中一定能听到开门播报"当成已验收功能**，它目前是"输出通道已实现、待复测"的状态。

**评委验收点**：异步幂等讲清了；预解码 + 叠加 + 限幅的机制讲清了；**主动声明了 8 kHz 限制**（这一条比讲得漂亮更重要）。

**我说**

> 再说视觉。检测走独立的采集支路，320 乘 180、每秒 2 帧，比通话视频低得多，用来控制推理开销。`pedestrain_detect.cpp` 第 113 到 141 行先跑**行人检测**，每个结果先过一层合理性过滤——分数、面积比例、宽高比、位置，把"整幅满屏框"这类假阳性挡掉，这个过滤器是为一次真实误报加的。第 143 到 159 行是**人脸存在检测**作近距离辅助：雷达正关注门前、或没有可信行人框时，同帧再跑人脸。第 163 行把候选交给 `vision_tracker.c`，用交并比跨帧关联，要求"4 帧窗口内至少 3 次命中"才确认；人脸框落在人体框内只算一人，避免重复计数。

**评委验收点**：帧结构与流式重同步讲清了；1 秒/2 秒/10 秒三个时间常量讲清了；四条件融合讲清了；主动区分"降低误触发"而非"无误报"。

> 接下来是工程质量。这个项目有一个刻意的做法：**把关键决策逻辑写成不依赖硬件、不依赖操作系统的纯函数**。来电策略、门锁状态机、雷达存在状态机、双证据融合、PCM 混音都是纯逻辑，因此可以在电脑上编译运行单元测试。`tests` 目录里一共十三个 C 单元测试文件，全部由十四个 Python 检查脚本自动编译执行——其中包括音频混音和行人假阳性过滤这两个专门为真实故障补上的测试——提交前实测**十四项全部通过、零失败**。构建方面，干净目录完成 1850 个步骤，固件约 6.56 MB，8 MB 应用分区还剩 18%；AI 检测约占 17% CPU，双核空闲率约 77% 和 98%。
>
> 最后我主动说明真实边界，这比被追问更好。第一，舵机是**空载模拟**门锁，没有真实锁体，也没有到位反馈。第二，摄像头只判断有没有人、有没有人脸存在，**不做身份识别**，网页上的百分比是模型置信分数而不是准确率。第三，雷达输出最多三个二维坐标点，**不是点云，也没有俯视轨迹**。第四，配套显示屏没有接入界面，屏幕只保留板级支持。第五，当前面向同一局域网内的**单客户端**，没有公网穿透、账号体系或云端推送。第六，开门命令目前没有鉴权、HTTPS 用的是演示用自签名证书，属于"可信局域网演示"的安全级别。第七，稳定性验证是连续约七分钟无异常，**还没有做 8 小时或 24 小时长稳测试**。
>
> 一句话总结：以官方门铃例程为基线完成 WT99P4C5-S1 移植，我自己做的是舵机模拟门锁、雷达二维感知、摄像头人员与视觉存在检测，并用"雷达加视觉"双证据驱动自动来电，同时为开门提示音做了预解码 PCM 输出通道。谢谢观看。

**评委验收点**：三条通道在网页端闭环了；纯函数可测的设计讲了；14 项检查与构建数据展示了；七条边界全部主动声明。

## 七、录制时可能被现场问题打断的准备

如果录制过程中被问（或自问自答）以下问题，直接用一句话回答，不要展开：

| 问题 | 一句话回答 |
| --- | --- |
| 为什么不用 RTSP/RTMP？ | 目标是与浏览器零插件互通，WebRTC 是唯一原生方案 |
| 为什么音频用 G711A 不用 OPUS？ | G711A 开销低、板端压力小；OPUS 分支已保留，可通过宏切换 |
| 为什么 AI 只有 2 帧？ | 检测是"证据"而不是"画面"，2 帧足够触发融合，同时保住通话实时性 |
| 雷达为什么不用 I2C？ | LD2450 只提供 UART 接口 |
| 断网了会怎样？ | 板端收到断开事件后停止 WebRTC；网页端 15 秒宽限后清理，重连后 SSE 自动恢复 |
| 两个浏览器同时打开？ | 当前是单客户端设计，新连接会接管 SSE，属于已知限制 |
| 重启后需要重新配对吗？ | 不需要，网页刷新即可；Wi-Fi 凭据优先使用应用配置，不依赖板端 NVS |
