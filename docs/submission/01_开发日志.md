## 二、选题与可行性分析

### 2.1 为什么选择这个项目

智能门铃同时涉及嵌入式音视频、网络通信、摄像头、麦克风、扬声器和执行机构，能够较完整地展示 ESP32-P4 的多媒体能力。官方示例已经提供 WebRTC 呼叫主链路，但默认硬件和目标作品不同，仍需要完成板级移植、硬件整合、交互补全与稳定性修复，因此既有可复刻基础，也有明确的二次开发空间。

### 2.2 原项目功能分析

| 原项目能力 | 本项目处理方式 |
| --- | --- |
| 局域网 WebRTC 门铃呼叫 | 保留，并适配 WT99P4C5-S1 |
| 摄像头视频与双向语音 | 保留，摄像头改为 OV5647，音频改为板载 ES8311 |
| 浏览器测试页面 | 保留并改为中文，增加状态提示与异常恢复 |
| BOOT 按键呼叫 | 保留，并修复刷新、断线和重复呼叫问题 |
| USB UVC 摄像头支持 | 本作品未启用，使用板载 MIPI-CSI 摄像头 |
| 门锁、雷达和视觉识别 | 原例程不包含，本项目自行增加 |

本作品不是对整个仓库所有解决方案的 100% 复制，而是以 `doorbell_local` 为基线完成可运行复刻，并在此基础上增加多模态感知和开门执行功能。

### 2.3 可行性判断

- WT99P4C5-S1 具有 ESP32-P4、32 MB PSRAM、板载 ESP32-C5、MIPI-CSI 和音频 Codec，资源能够覆盖本地 WebRTC 音视频需求。
- OV5647、ES8311 和 ESP32-C5 都有 ESP-IDF 组件支持，可以通过板级配置完成移植。
- HLK-LD2450 提供 UART 坐标数据，舵机只需要一路 50 Hz PWM，扩展接口数量足够。
- 主要风险是 P4 芯片版本兼容、音视频实时性、AI 推理开销、舵机电源干扰和多状态同步，均可通过分阶段验证降低风险。

## 三、硬件搭建

### 3.1 物料清单

| 类别 | 型号或规格 | 用途 |
| --- | --- | --- |
| 主板 | WT99P4C5-S1 1V1，ESP32-P4 rev 1.3，16 MB Flash，32 MB PSRAM | 主控、音视频处理与网页服务 |
| 无线芯片 | 板载 ESP32-C5，四线 SDIO | Wi-Fi 网络连接 |
| 摄像头 | OV5647，MIPI-CSI | 远程视频与视觉检测 |
| 音频 | ES8311、板载麦克风、4 Ω 3 W 扬声器 | 双向通话、铃声与开门播报 |
| 舵机 | MG90S/GX90S 类 180°模拟舵机，4.8～6 V | 模拟门锁开合 |
| 雷达 | HLK-LD2450，5 V，UART 256000 baud | 门前目标坐标与进入/离开检测 |
| 电源板 | 三路可调降压模块，输入 6～24 V | 为舵机和雷达提供稳压 5 V |
| 适配器 | 9 V / 2.22 A | 电源板输入；5 V / 3 A 时应绕过降压模块 |

### 3.2 接线与供电

所有接线均在断电状态完成。

| 设备端 | 主板或电源端 |
| --- | --- |
| OV5647 排线 | 主板 `MIPI_CSI` 接口 |
| 4 Ω 3 W 扬声器 | 主板 `SPK` 接口 |
| 舵机黄色/橙色 PWM | J6 pin 20 / ESP32-P4 GPIO32 |
| 舵机红色电源线 | 稳压 5 V 输出正极 |
| 舵机棕色/黑色 GND | 稳压电源输出负极 |
| LD2450 TX | J6 pin 10 / ESP32-P4 GPIO4（UART1 RX） |
| LD2450 RX | J6 pin 12 / ESP32-P4 GPIO5（UART1 TX） |
| LD2450 5V | 稳压 5 V 输出正极，单独分支 |
| LD2450 GND | 稳压电源输出负极 |
| 电源板 OUT- | 主板 J6 pin 11/13/15/17 任一 GND，共地 |

调试阶段主板由 USB-C 单独供电，9 V 适配器接降压模块输入，模块调整为 5 V 后给舵机和雷达供电。外部 5 V 不与主板 USB 5 V 并联，但所有设备必须共地。舵机电流变化较大，因此与雷达分支布线，避免串口乱码和主板复位。

### 3.3 硬件验收

先不连接舵机和雷达，烧录厂商例程，分别确认摄像头、屏幕接口、扬声器、麦克风、PSRAM 和 P4-C5 通信正常。随后逐个增加舵机和雷达，每增加一个设备就单独测试，避免同时出现问题时无法定位。

## 四、软件开发过程

### 4.1 开发环境

- Windows 11 / PowerShell。
- ESP-IDF v5.5.5。
- ESP-IDF 自带 Python 3.11 环境。
- CMake、Ninja、Git。
- Chrome 或 Edge 浏览器。

### 4.2 WT99P4C5-S1 板级移植

项目先从厂商例程确认硬件，再把 `doorbell_local` 适配到 WT99P4C5-S1：

- 摄像头配置为 OV5647 RAW10 1280×960。
- Flash 设置为 16 MB，启用 32 MB PSRAM。
- ESP32-C5 SDIO 引脚设置为 CLK18、CMD19、D0～D3 为 14～17、复位 54。
- 增加 WT99P4C5-S1 音频板定义：I2C 7/8，I2S 13/12/10/9/11，功放使能 53。
- Wi-Fi 凭据从源码中分离到被 Git 忽略的 `settings.local.h`。

启动日志最终可以识别 ESP32-P4 rev 1.3、32 MB PSRAM、ESP32-C5、OV5647、ES8311 和 HTTPS 服务。

### 4.3 WebRTC 门铃主链路

实现并验证如下闭环：浏览器访问板端 HTTPS 页面 → BOOT/GPIO35 触发来电 → 浏览器接听或拒绝 → 建立 H.264 视频和双向音频 → 挂断 → 再次呼叫。

初版呼叫经常需要约 30 秒，视频还会晚于音频出现。局域网模式取消公网 STUN 等待，并移除浏览器端无用的摄像头采集后，多轮实测建立时间缩短为 4 秒、6 秒和 4 秒。

随后增加 SSE 连接替换、15 秒瞬时断线宽限、确认式挂断和媒体元素清理，解决网页刷新后首次来电丢失、通话意外断开、页面显示结束但视频仍播放等状态不同步问题。

### 4.4 音频提示与呼叫同步

最初开门语音只能在通话结束后播放，因为提示音会抢占 WebRTC 音频渲染器。项目新增 PCM Overlay，把“Doors open, come in please”混入正在播放的通话 PCM 流，使通话继续进行时也能听到开门播报。

门铃声由板端状态控制：板端播放约 4 秒后发送 `RING_STOPPED`，网页随即停止铃声；网页另保留 4.5 秒超时保护，避免异常情况下持续响铃。

### 4.5 舵机模拟门锁

舵机使用 GPIO32 输出 50 Hz PWM，500 μs 为锁定位置，2500 μs 为打开位置，打开后保持 5 秒再自动返回。软件状态包含 `LOCKED`、`OPENING`、`UNLOCKED`、`CLOSING` 和 `FAULT`。

调试中曾将动作异常误认为舵机堵转，后来发现网页实际持续返回 `Door operation failed`。修正命令调用和状态返回后，空载舵机开门流程恢复正常。本次提交不安装真实门锁，也不宣称具备锁舌到位反馈。

### 4.6 HLK-LD2450 雷达

雷达使用 UART1，256000、8N1，解析器可处理 30 字节目标帧、串口分片、前导噪声和最多三个目标。门前区域设置为 X=-1500～1500 mm、Y=300～3000 mm；目标持续进入 1 秒后确认，持续离开 2 秒后确认，再次触发冷却时间为 10 秒。

网页显示目标 X/Y 坐标、速度和进入/离开事件。事件数量表示历史状态变化的累计条数，不是当前人数。当前雷达只能给出二维目标点，不能生成三维点云或人体轮廓。

### 4.7 摄像头检测与多模态融合

纯运动检测容易把光照变化、窗帘和静态物体误判为人，因此加入 ESP-DL 行人检测与人脸存在检测。远程视频保持 640×480、15 FPS，独立检测支路使用 320×180 RGB565、2 FPS；结果经过置信度、面积、边界框和连续帧确认，再通过 SSE 叠加到网页视频上。

系统只判断“是否有人”，不做人脸身份识别。行人模型是主要判断，人脸模型只作为近距离辅助；雷达和摄像头结果经过策略融合后触发一次门铃，减少单帧或单传感器误触发。人脸身份识别和配套屏幕 UI 保留为未来扩展项。

## 五、整合调试与问题汇总

| 问题现象 | 原因定位 | 解决办法 | 结果 |
| --- | --- | --- | --- |
| 普通 PowerShell 提示找不到 `idf.py` | ESP-IDF 环境未初始化，并混用了 PowerShell 与 CMD 变量语法 | 统一从 ESP-IDF v5.5.5 命令行进入工程 | 可正常配置和构建 |
| 固件拒绝烧录 P4 rev 1.3 | 构建配置要求更高芯片 revision | 将目标 revision 调整为 ESP32-P4 v1.x，重新构建 | 无需长期使用 `--force` |
| 首次接听约 30 秒且视频晚到 | 公网 STUN 等待和浏览器额外媒体采集 | 局域网模式取消公网 STUN，关闭无用本地摄像头 | 多轮约 4～6 秒接通 |
| 刷新网页后第一次 BOOT 无来电 | 旧 SSE 客户端未及时释放 | 新连接替换旧连接并清理状态 | 刷新后可再次触发 |
| 通话中开门没有语音，挂断后才播 | 提示音与 WebRTC 播放器争用音频通道 | 在通话 PCM 中混入提示音 | 通话不中断且能听到播报 |
| 网页持续提示 `Door operation failed` | 舵机命令路径和状态返回不一致 | 修正调用、状态机和返回结果 | 点击开门动作正常 |
| 雷达离开事件出现乱码，事件数持续增加 | 字符编码显示错误，且事件数被误解为实时人数 | 中文化事件文本，明确其为有限历史记录 | 页面可读且含义明确 |
| 页面显示“通话结束”但视频仍在 | 仅更新了界面状态，媒体连接未完全关闭 | 板端确认挂断并清理 PeerConnection 和视频元素 | 通话与界面同步结束 |
| 网页卡顿、BOOT 失效、视觉检测无结果 | AI 线程 4 KB 栈不足，浮点格式化触发 Stack protection fault | 栈增至 24 KB、JSON 改静态缓存、整数化格式、固定 RGB565LE | 连续观察约 7 分钟无异常 |

## 八、已知边界

- 当前是同一局域网内的单客户端演示，不包含公网穿透、账号体系和云端推送。
- 人体检测精度仍受光线、拍摄角度、遮挡和 320×180 检测分辨率影响。
- 雷达展示的是二维目标坐标和轨迹事件，不是三维点云。
- 舵机没有电流、位置或限位反馈，不能证明真实锁舌已经到位。
- USB UVC 未启用，使用板载 MIPI-CSI 摄像头。
- 尚未完成正式的 8 小时或 24 小时连续稳定性测试。
- 当前未安装真实门锁、未实现人脸身份识别，也未开发配套屏幕界面。

## 九、总结与反思

本项目从“让官方示例在另一块板上运行”逐步扩展为一个包含音视频、执行机构和多传感器判断的完整演示。开发中最重要的经验是先分离验证硬件，再逐层叠加功能；实时系统的问题往往不是单一模块错误，而是线程栈、音频资源、网页状态和网络时序共同作用的结果。

最终作品完成了原始门铃示例的核心闭环，并形成了舵机开门、雷达目标坐标、摄像头人体存在检测和多模态触发等差异化功能。仍需改进的方向包括更长期的稳定性数据、更精确的人体检测、更直观的雷达俯视轨迹、真实门锁反馈、人脸身份识别和屏幕端交互。
