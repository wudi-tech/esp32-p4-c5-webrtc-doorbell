# 行人假阳性过滤器

日期: 2026-09-08  
董事会: WT99P4C5-S1, ESP32-P4 订正 1.3  
串行端口: COM5  
固件构建时间: `Sep 8 2026 11:09:58`

## 复制原因

镜头前没有人， 行人模型一再返回
近320x180的探测器 RGB565 探测器框架：

```text
score=0.852 box=[0,0,319,179]
score=0.829 box=[0,0,319,179]
```

之前的整合 立即接受了每个模式的结果， 这样
这种不可思议的全帧盒刷新相机持续存在，
创建错误的浏览器事件。

## 已执行警卫

探测器的集成现在应用了所有这些条件
应用程序检测回调：

- 至少得分数 0.75;
- 有效的框架坐标;
- 框区域从 0.5%通过85%的探测器框架;
- 连续3名候选人，至少25%的交叉结合;
- 三个框漏后清晰确认状态。

拒绝的模型输出在序列日志中是限速的，所以断层仍然存在
在没有淹没控制台的情况下观察。

## 核查

- 主机行人过滤测试: 通过。
- 完成现有的门铃 Python 验证套件: 通过。
- ESP-IDF 5.5.5 构建: 通过 (`doorbell_demo.bin` `0x65e270`, 20%的应用分机头室)。
- COM5 烧录: 通过 (6,677,104 应用程序字节; 已校验散列)。
- 空场靴观察: 驳回全面结果; 没有发布行人事件。
- 空场 Wi-Fi 重新连接观测: 探测器重新启动并再次拒绝同一结果。

手动接受真实阳性: 清除浏览器历史， 站稳了
至少两秒钟， 然后离开. 一个组合镜头人集
应显示， 当空场景不添加事件时。
