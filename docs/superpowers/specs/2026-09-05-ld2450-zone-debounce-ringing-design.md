# LD2450 关注区域、去抖与雷达来电设计

日期：2026-09-05  
范围：任务 8.2  
状态：设计已确认，待实现

## 目标

在 WT99P4C5-S1 已能稳定解析 LD2450 数据帧的基础上，把雷达目标转换成可靠的门前存在状态。真人持续进入关注区域后，系统复用现有门铃入口触发一次来电和铃声；单帧噪声、短暂丢帧、持续停留及短时间重复进出不得造成连续呼叫。

任务 8.2 只负责本地判定和复用现有 `RING` 来电链路。结构化雷达事件的网页展示、SSE 或 WebRTC 数据通道传输属于任务 8.3，不在本次范围内。

## 默认参数

所有参数集中定义，后续可以根据实测调整：

- 关注区横向范围：`-1500 mm <= x <= 1500 mm`
- 关注区纵向范围：`300 mm <= y <= 3000 mm`
- 进入确认时间：`1000 ms`
- 离开确认时间：`2000 ms`
- 离开后的重复来电冷却时间：`10000 ms`
- 方向静止死区：`-10 cm/s` 到 `10 cm/s`

边界值属于关注区。无效目标和区域外目标不计入存在判定。

## 方案选择

采用独立、按单调时钟工作的时间状态机，而不是按帧数或直接在串口回调中触发。

选择该方案的原因：

- 雷达数据可能分批读取，按帧数去抖会使实际时间随调度和串口读取方式变化。
- 协议解析、存在判断和门铃业务保持分层，便于分别测试。
- 状态变化只在确认边沿产生事件，可以天然避免每帧重复响铃。

## 模块边界

### `radar_ld2450`

继续负责 UART 接收、流式组帧和 LD2450 协议解析。每个合法帧交给存在融合模块处理；损坏帧不改变存在状态，也不推进确认计时。

### `presence_fusion`

新增 `presence_fusion.c` 和 `presence_fusion.h`，实现不依赖 FreeRTOS 或 ESP-IDF 的纯 C 状态机。输入包括解析后的目标数组和单调毫秒时间；输出包括状态变化、代表目标、方向和是否请求来电。

该模块不直接调用 WebRTC、播放器或 GPIO。这样可以在 Windows 主机上用固定时间序列进行单元测试。

### 门铃集成层

雷达模块收到 `ring_requested` 后，通过一个安全的门铃请求入口复用现有 `RING` 行为：向网页发送 `RING`，并播放板载 `ring.aac`。

门铃请求入口必须先检查 WebRTC 是否已经初始化以及门铃是否空闲。尚未初始化、正在响铃、正在连接或已通话时，不重复发起来电，并输出明确的抑制原因。这样可避免雷达在开机早期或通话期间访问无效句柄、重入呼叫。

BOOT 按键仍使用同一门铃业务入口，保持人工按键与雷达触发的一致行为。

## 状态机

状态包括：

- `CLEAR`：关注区内无人。
- `ENTERING`：检测到区域内目标，但尚未持续满 1 秒。
- `PRESENT`：目标已连续存在满 1 秒。
- `EXITING`：目标暂时消失，但尚未持续满 2 秒。

转换规则：

1. `CLEAR` 检测到任意区域内目标时进入 `ENTERING`，记录进入候选时间。
2. `ENTERING` 连续有区域内目标满 1000 ms 时进入 `PRESENT`，产生一次 `ENTER_CONFIRMED`。
3. `ENTERING` 在确认前无人时立即回到 `CLEAR`，不产生事件。
4. `PRESENT` 暂时无人时进入 `EXITING`，记录离开候选时间。
5. `EXITING` 在 2000 ms 内重新检测到区域内目标时回到 `PRESENT`，不产生新的进入事件或来电。
6. `EXITING` 连续无人满 2000 ms 时进入 `CLEAR`，产生一次 `LEAVE_CONFIRMED`，并从此时开始 10 秒冷却。

一次 `PRESENT` 周期最多请求一次来电。在冷却期内确认的新一轮进入仍记录 `ENTER_CONFIRMED`，但 `ring_requested` 为假；即使冷却随后结束，也不会对这次持续停留补发来电。目标必须完成一次确认离开，并在冷却结束后再次进入，才会产生新的来电请求。

系统首次启动没有人为冷却，第一次有效进入可以触发来电。

## 多目标与方向

存在状态基于“至少一个有效目标位于关注区”，不依赖 LD2450 的目标槽位编号。因此一个目标离开、另一个目标仍在区域内时，整体状态保持 `PRESENT`。

用于日志和后续 任务 8.3 的代表目标取区域内 `y` 最小的有效目标，即距离雷达前方最近的目标。方向按雷达上报速度分类：

- `< -10 cm/s`：`APPROACHING`
- `-10 cm/s` 到 `10 cm/s`：`STATIONARY`
- `> 10 cm/s`：`LEAVING`

该方向只作为观测信息，不参与本次响铃门限，避免侧向进入或速度符号偶发变化导致漏报。雷达安装方向应面向门外；速度方向将在实机日志中复核，若安装方向与定义相反，只调整分类映射，不改变存在状态机。

## 数据流

1. UART 任务收到字节流。
2. `radar_ld2450` 组帧并解析最多三个目标。
3. UART 任务取得单调毫秒时间，把当前帧交给 `presence_fusion`。
4. `presence_fusion` 判断区域、更新计时和状态，并返回状态变化结果。
5. 每次状态变化输出一条简洁日志；不再为每一帧打印完整目标信息。
6. 仅当结果为 `ENTER_CONFIRMED` 且 `ring_requested=true` 时，调用安全门铃请求入口。
7. 门铃入口接受请求后，网页获得现有 `RING` 命令，板载扬声器播放现有铃声。

## 异常处理

- 非法帧：丢弃并继续同步，不改变状态。
- 短暂目标丢失：由 2 秒离开确认吸收。
- 多个目标或槽位变化：使用区域内任意目标维持存在状态。
- 时间计数回绕：使用无符号时间差比较，不直接比较绝对时间大小。
- WebRTC 未初始化：抑制来电并记录 `not ready`，不得崩溃。
- 门铃正忙：抑制重复来电并记录 `busy`。
- 来电发送失败：记录错误；本次停留不进行高频重试，防止事件风暴。
- UART 长时间无数据：记录传感器离线诊断，但不得把通信故障伪装成新的来电事件。

## 测试设计

### 主机单元测试

为 `presence_fusion` 使用构造目标和模拟毫秒时间，至少覆盖：

- 区域内外及四条边界。
- 999 ms 不确认，1000 ms 确认进入。
- 进入确认期间短暂消失后重新计时。
- 1999 ms 不确认离开，2000 ms 确认离开。
- `EXITING` 期间目标恢复后回到 `PRESENT`，不重复来电。
- 持续停留产生且只产生一次来电请求。
- 冷却期内重新进入有事件但无来电。
- 冷却结束后完成新的进入流程可再次来电。
- 多目标中任意一个留在区域内时不确认离开。
- 目标槽位变化不制造额外进入事件。
- 毫秒计数接近 `UINT32_MAX` 时仍能正确计算持续时间。

门铃请求入口通过可替换依赖或窄接口测试 `not ready`、`busy` 和正常接受三种结果。

### 构建与实机验证

1. 运行已有 LD2450 parser、门锁及板级配置回归测试。
2. 完整构建 ESP32-P4 固件并检查镜像大小。
3. 烧录 COM5，确认启动、Wi-Fi、WebRTC 和 UART 均正常。
4. 打开现有测试网页，分别执行快速掠过、持续进入、短暂遮挡、离开后快速重入、冷却结束后再次进入。
5. 验证网页来电状态与板载铃声同步出现，一次停留只出现一次。
6. 至少连续完成三轮“进入—接听或挂断—离开”，主板不得复位。

## 验收标准

- 区域外活动不触发来电。
- 区域内持续不足 1 秒不触发来电。
- 区域内持续满 1 秒触发一次现有门铃来电和铃声。
- 2 秒以内的短暂目标丢失不结束本次停留，也不重复来电。
- 确认离开后 10 秒内重新进入不重复来电。
- WebRTC 未就绪或正忙时系统稳定，无空句柄访问或重复呼叫。
- 主机测试、完整固件构建和实机三轮验证全部通过后，任务 8.2 才标记完成。
